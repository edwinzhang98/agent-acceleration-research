# 文献自己怎样定义"agent 加速"：问题、挑战与解法的脉络（讨论稿）

2026-09-30，Claude Code 会话。Edwin 的问题：抛开我们自己的时间/费用测量口径——那只是一种口径——只从我们经手过的文献看，如果要讲"agent 加速"这个题目，这些文章是怎样定义问题的，它们说的普遍挑战是什么，各自的解法又是怎样从定义和挑战接过来的；把这条脉络整理出来。本文按"先看文献怎么说，再归纳"的顺序写；文末附证据索引和完整参考文献。不改 slides，不改方案稿。

## 读法与来源

- **标签。** **文献陈述**（论文自己的说法，带证据编号）；**我的判断**（对记录的归纳、计数或解读）；**用户要求**（Edwin 明确说过的）。
- **材料。** 两部分：(1) slides 第一、二部分引用的文献（`slides/build_deck.py` 的 REFS_P1、REFS_P2，去重后 114 项，其中论文 98 篇：13 篇此前已有全文记录，85 篇本次下载全文；厂商定价页、产品文档等 16 项不算"定义问题的文献"，不在本文范围）；(2) 第三部分核对库里读过全文的 378 篇（w/n/g/h/x/s 六个批次，含自改进综述那一批；两页 SAP 产品页除外）。合计 463 条定位记录，对应 432 篇不同的工作（同一工作的多份记录——正式版与预印本、补充条目——分开保存、合并计数）。
- **方法。** 每篇由一名读者只读摘要、引言和问题定义（或预备知识）部分，写一条"定位记录"：论文陈述的问题、它归因的瓶颈、正式的目标或指标（有公式的抄公式并逐个解释符号）、解法怎样回应瓶颈、声称改善的量，每一项锁定到全文文本的行号并附原文锚点；脚本核对每个锚点确实在该行（463 条、2,311 个锚点，0 个不符）。独立审计（第二名读者逐项反驳、改正）覆盖全部 463 条：231 条由 Claude 的审计 agent 完成（slides 那 85 篇全部、核对库 146 篇，含本文引用到的全部记录），其余 232 条在 Edwin 把 Claude 额度留给主会话后改由 Codex（gpt-6-astra）按同一套规则完成；其中 25 条被驳回，全部因为来源不是论文（公司博客、产品文档、README、定价页），不能修成论文记录，它们不进记录文件、本文也没有引用。审计后锚点复核 2,314 处，0 处不符。之后按论文自己的"位置"和"效率是否在所陈述的问题里"分组，三名分类者分别给效率居中心的 160 条、次要的 246 条、无关的 57 条做家族划分；家族的写法和跨家族的归纳由本会话完成。
- **证据规则。** 只用定位记录里的陈述；方括号里的 f 编号指向附录 A 的证据索引（#0 问题陈述、#1 归因、#2 目标、#3 解法、#4 改善量、#5 读者分类）。"没有找到"只在"本文核对过的文献里"这个范围内成立。来源等级按 Edwin 9 月 30 日的引用优先级判定；不合格来源在本文只作描述、不进入结论、不带编号（第 8 节）。
- **术语。** 本文用论文自己的词说效率的量（延迟、端到端时间、费用、token、调用次数、步数、样本效率、搜索开销）；不用 slides 里的 I–VI 项和 t03–t13 杠杆，它们只在第 7 节对照时出现。

## 要点（我的判断）

1. **文献里没有一个统一的"agent 加速"定义。** 432 篇里，把速度、费用、token、调用或步数写进所陈述问题的有 151 篇（记录 160 条），只当作附带量的 228 篇，完全不谈的 53 篇。就连"加速"要减少的量，各家也不同：费用（355 条记录提到）、时间或延迟（306）、token（229）、步数（195）、调用次数（194）、样本或 rollout（125）、算力（124）。
2. **定义分成 11 个家族，沿着流水线排开**：推理服务看不到 agent 负载的结构（F1）；对每个查询和步骤一律投入同样的算力（F2）；模型与工具串行等待（F3）；每个原子动作都调用一次模型（F4）；每次调用读入的上下文过长或越来越长（F5）；环境和工具执行本身慢（F6）；跨任务重复摸索、不复用过往执行（F7）；改进产物本身抬高运行成本（F8）；构建和改进 agent 的过程贵（F9）；评测与标注贵（F10）；只看结果的评测让效率不可见（F11）。每个家族里，"问题怎么陈述"决定了"解法长什么样"：F3 的解法都是投机或异步，F4 的解法都是提高动作粒度或一次生成整段程序，F7 的解法都是把执行过的东西存成可复用的工作流、技能或程序。
3. **他们共同指认的挑战只有三条**：模型是无状态的、按 token 计价的、串行的决策者，被放进一个循环里反复调用；循环的每一圈都带着越来越长的历史；同样的工作被反复支付（跨步、跨任务、跨 agent、跨调用的 KV）。其余分歧不少：延迟到底被解码、工具等待还是推理占大头，三组论文各执一词；记忆和技能模块在等预算下是否值回 token，有直接的否定证据；按失败归责分配搜索预算是否有用，也有否定结果。
4. **给"加速"写出正式目标函数的只有少数**：带预算约束的准确率（FrugalGPT、Budget-Aware Tool Use、GEPA、HarnessLens）、成功减去 λ 乘费用（BoPO、Ares）、每次成功的费用 cost-of-pass、准入分含延迟和 token 项（SEDM）、带成本项的双目标（FRAMES，暂缓）、效用加权和（SICA）。多数论文只报指标不写目标。
5. **定义和解法之间有两处断裂**：一边是"只看结果的评测让效率不可见"（F11）和"改进产物抬高运行成本"（F8）这两个定义，对应的"解法"只是新指标、新记账，还没有优化方法；另一边是不少优化方法（尤其厂商文档和一些技能/记忆论文）优化了某个量却没有陈述问题（第 6 节）。

## 2 效率居中心的 160 条：11 个定义家族

每个家族按同一格式：文献怎样陈述问题 → 把原因归到哪里 → 正式的目标（有则列）→ 解法怎样从挑战接过来 → 声称改善的量 → 分歧。引用只指向定位记录（附录 A）。

### F1 推理服务引擎看不到 agent 负载的结构（17 条）

**怎样陈述问题（文献陈述）。** 推理系统是为单请求聊天设计的，把每次工具调用或每轮结束当作请求结束，而 agent 程序发出许多相互依赖、夹着工具暂停、共享长前缀的调用：InferCept 说现有系统把每次"拦截"当作生成结束、拦截后重新组成请求 [E1314]；Continuum 说轮末驱逐 KV 在 agent 负载下失效，因为工具调用带来的暂停阻断了跨轮复用 [E1315]；Autellix 说服务系统忽略程序与调用之间的依赖，只优化单个调用 [E1316]；Parrot 说应用只能用请求级 API，服务端丢失了应用级信息 [E1317]；KVFlow 说前缀缓存在 GPU 内存有限时被 LRU 驱逐拖累 [E1318]。这里"效率"的量是服务层的：吞吐、作业完成时间、TTFT/TPOT、prefill 延迟、GPU 内存浪费。

**归因（文献陈述）。** 请求级的短视：拦截被当作请求结束，于是前缀重算 [E1319]；驱逐后要重算 prefill 或从 CPU 回载，回来的请求还要排队等 GPU 内存，逐轮累积 [E1320]；调用级和程序级的队头阻塞 [E1321]；服务不知道请求之间的关联，就抓不住依赖、端到端调度和公共前缀三个机会 [E1322]；LRU 不知道哪个 agent 接下来要跑，常在复用前夕把它的缓存丢掉 [E1323]。

**正式的目标（文献陈述）。** InferCept 把"最小化拦截造成的 GPU 内存浪费"写成三种处理（丢弃、保留、换出）各自的浪费公式（式 1–3）[E1324]；Continuum 的 TTL 选择是 τ* = argmax_τ P(τ,f)·Benefit(r) − Cost(τ,r)，Cost 是占用内存与时长之积、Benefit 是缓存缺失和乱序两项代价 [E1325]；Autellix 把程序的端到端延迟拆成等待、执行、拦截三段来最小化 [E1326]；Parrot 让应用给输出变量标注端到端延迟或吞吐目标 [E1327]。

**解法怎样接上（文献陈述）。** 跨工具暂停保住 KV（按浪费选处理方式、TTL 钉住、按工作流驱逐）[E1328, E1329, E1330]；把程序当作一等调度单位（程序级优先级、语义变量恢复依赖）[E1331, E1332]。

**改善的量（文献陈述）。** 服务吞吐 1.6–2×（InferCept）[E1333]；作业完成时间 1.12–3.66×、吞吐 1.10–3.22×（Continuum）[E1334]；程序吞吐 4–15×（Autellix）[E1335]；端到端 11.7× 或吞吐 12×（Parrot）[E1336]；单工作流 1.83×、并发 2.19×（KVFlow）[E1337]。

**分歧（我的判断）。** 同一家族里，端侧的 Agent-X 说 agent 的延迟在 prefill 和 decode 两段都重（输入远长于输出）[E1338]，而 ToolSpec 说生成工具调用占端到端延迟约 80%、是工具执行的 4 倍 [E1339]；TraceLab 不优化，只给出编码 agent 的负载特征（上下文逐会话增长、重复工具调用压在两种服务基础设施上）[E1340, E1341]。

### F2 对所有查询和步骤一律投入同样的算力（12 条）

**怎样陈述问题（文献陈述）。** 费用—质量的取舍在"每个查询或步骤该给多少能力"：FrugalGPT 说 API 费用相差两个数量级，问的是怎样既便宜又准 [E1342]；RouteLLM 说全走最强模型贵得不可持续、全走小模型又在难题上掉质量 [E1343]；Step-level Optimization 说计算机使用 agent 几乎每一步都调用大型多模态模型，所以又贵又慢 [E1344]；BoPO 把它写成 agent 场景：每一步都调高能力模型不可持续，全用便宜模型又会在少数关键步失败 [E1345]；Budget-Aware Tool Use 说单纯加大工具调用预算没用，因为 agent 没有预算意识 [E1346]；Ares 和 TSDS 说思考模型在每一步都堆推理 token [E1347, E1348]；Runaway 说 agent 陷在重复循环里产生冗余开销 [E1349]。

**归因（文献陈述）。** 固定策略忽视了异质性：GUI 轨迹里很多步是例行的、失败集中在少数高风险时刻 [E1350]；推理在动作已经收敛之后仍在继续 [E1351]；不是每一步都需要同样程度的思考 [E1352]；agent 认不出自己卡住了 [E1353]；agent 场景的路由是序贯的、路径依赖的，早期错误会累积、回报只在末尾 [E1354]。

**正式的目标（文献陈述）。** FrugalGPT：max E[r(a, â(s,q))] s.t. E[c(s,q)] ≤ b，q 查询、â 策略 s 的答案、c 费用、b 平均费用上限 [E1355]；RouteLLM：在达到目标质量（如强模型的 90%）下最小化费用，路由规则按学到的胜率阈值 [E1356]；BoPO：J_soft(θ) = E[𝟙(success) − λ Σ c(a_t)]，λ 是拉格朗日乘子、扫描它得到效率前沿 [E1357]；Ares：max E[V(τ,x) − λ Σ cost(e_t)]，e_t 是每步的推理档位 [E1358]；TSDS：min C_L(λ) s.t. R(λ) ≥ R^min，C_D(λ) ≤ C_D^max，即在回报和上云率约束下最小化本地思考量 [E1359]；Budget-Aware Tool Use：max Acc_b(π) s.t. 每种工具的调用数 ≤ b_i [E1360]；Step-level Optimization：按"卡住"概率超过阈值才把控制权交给大模型 [E1361]。

**解法怎样接上（文献陈述）。** 按查询路由或级联 [E1362, E1363]；在一个 episode 内按步升级（小模型默认、监视器触发大模型）[E1364, E1365]；按步选推理档位、本地收敛探针加上云判据 [E1366, E1367]；预算信号和停止规则 [E1368, E1369]。

**改善的量（文献陈述）。** 同等准确率下费用 −98%（FrugalGPT）[E1370]、GPT-4 调用 3.66×（RouteLLM）[E1371]、推理费用 −74.6%、延迟 −45.8%（Step-level）[E1372]；推理 token −52.7%（Ares）[E1373]、−43–65%（TSDS）[E1374]；冗余步 −50–70%，成功率略降（Runaway）[E1375]。

**分歧（文献陈述）。** BoPO 明说单轮路由搬不到 agent 上，因为分配的单位是路径而不是查询 [E1354]；Budget-Aware Tool Use 说 agent 不会用多出来的预算，Runaway 说 agent 不会停——一个嫌它花得少、一个嫌它花得多，指向的是同一个缺陷：agent 没有对预算的感知 [E1376, E1353]。

### F3 agent 循环里模型与工具串行依赖（12 条）

**怎样陈述问题（文献陈述）。** 思考—动作—观察循环是串行的：模型解码、发出工具调用、空等结果、再继续，端到端时间是模型时间与工具时间之和。SPORK 量了工具等待占其负载墙钟的 16–37%（此前报告 35–61%）[E1377]；Asynchronous Function Calling 说每次调用都阻塞推理 [E1378]；LLMCompiler 说逐个函数串行推理和执行带来高延迟和高费用 [E1379]；Speculative Actions 说每一步环境交互都有不可忽略的往返时间 [E1380]；Speculative Tool Execution 说等待工具的时间越来越占主导 [E1381]；ParaGUI 说 GUI agent 把长任务当作串行的感知—决策—动作链 [E1382]。

**归因（文献陈述）。** 严格的串行依赖：每个工具结果决定之后的全部 token，调用发不出去解码就不能结束，结果不回来下一步就不能开始，token 级投机解码消不掉这种跨步依赖 [E1383, E1384, E1385]；同步协议让执行器必须按发起顺序完成 [E1386]。

**正式的目标（文献陈述）。** SPORK：延迟比 Ratio = T_base / (T*_base − α·t_overlap + T_oh)，上限 1/(1 − f_tool)，α 是投机被接受的比例、f_tool 是工具时间占比 [E1387]；AsyncLM 以 makespan 为训练目标，并给出同步与异步的解析式 [E1388]；Speculative Planning 写出无投机与有投机的计划时间之和 [E1389]；Speculative Actions 给出算法与串行执行的期望运行时间比（命题 1）[E1390]；LLMCompiler 给出 N 个可并行任务下的延迟模型 [E1391]；ParaGUI 定义步数缩减比 S = L_serial/L_parallel [E1392]。

**解法怎样接上（文献陈述）。** 用便宜的预测器猜下一个工具调用或观察、猜对就提交（无损投机）[E1393, E1394, E1395]；用快的近似 agent 做投机规划 [E1396]；非阻塞的函数调用与可中断解码 [E1397]；把独立调用编译成 DAG 并行执行 [E1398]；把长任务拆给并行的 GUI 工作者 [E1399]。

**改善的量（文献陈述）。** P95 延迟 −18%（SPORK，对 vLLM 自带的 n-gram 投机）[E1400]；端到端 1.6–5.4×（AsyncLM）[E1401]；延迟 3.7×、费用 6.7×（LLMCompiler，对 ReAct）[E1402]；最多 20%（Speculative Actions）[E1403]；6–21%（客户端投机）[E1404]；总运行时间 −20–42%（Speculative Planning）[E1405]；关键路径步数减半（ParaGUI）[E1406]。

**分歧（文献陈述）。** 什么占延迟大头：SPORK 与 Speculative Tool Execution 盯工具等待 [E1377, E1381]，ToolSpec 说生成工具调用约占 80% [E1339]，ParaGUI 引 OSWorld-Human 说 LMM 推理占每任务延迟的 75–94% [E1407]。三者的负载不同（搜索 agent、API 工具、GUI），这本身说明"瓶颈在哪"随负载而变，不是一个常数。

### F4 每个原子步骤都调用一次大模型（18 条）

**怎样陈述问题（文献陈述）。** 逐步决策的粒度太细：agent 每一轮读屏、推理、发出一个低层动作，延迟、token 和调用数随原子步数增长。AppAgentX 说逐步推理对例行任务低效 [E1408]；AutoDroid-V2 说逐步查询模型在端侧算不动 [E1409]；AXIS 说 UI 是为人设计的，完成一件事要多次交互、每次交互一次调用 [E1410, E1411]；Act More Decide Less 说 ReAct 一轮一个原子动作，很多轮花在例行序列上 [E1412]；GraphPilot 说逐步查询累积网络延迟 [E1413]；Agent JIT 说每次迭代一次调用、又慢又错 [E1414]；Skim 说每任务 30–120 秒、0.2–0.5 美元，而这不是任务固有的，是 agent 的组成方式造成的 [E1415]；AutoTool 说工具选择反复调用模型是主要瓶颈 [E1416]；Growing Harness 说框架反复让模型在每个任务里重建同样的控制决策 [E1417]。

**归因（文献陈述）。** 动作接口过细、每步都当决策：原子动作集迫使动作链变长，每步都要一次完整推理，哪怕这一步是机械的、有规律的或确定性的 [E1418, E1419, E1420]；每次查询只带有限上下文，所以要多次增量查询 [E1421]；把重复的控制交给模型，每次决策都是一次调用、都在增长上下文 [E1422]。

**正式的目标（文献陈述）。** Agent JIT 的规划器在候选计划里取加权调用数最小者，工具调用和模型调用按深度折扣计权 [E1423]；Act More Decide Less 训练损失 L = L_on + λ L_off，指标是每回合的决策轮数 [E1424]；AutoTool 把问题定义为从历史轨迹预测下一个 (tool, params) [E1425]；Growing Harness 的规则是"成功优先"：只在留出门集上成功率不降才保留修补，费用只作记录 [E1426]；其余多数只报步数、时间、token、调用数（AppAgentX、AXIS、GraphPilot、Skim）[E1427, E1428, E1429, E1430]。

**解法怎样接上（文献陈述）。** 提高动作抽象：学到的工具、API、快捷动作替代原子动作链 [E1431, E1432]；一次生成整段脚本或程序、不逐步调用 [E1433, E1434, E1435]；预测或缓存例行决策而不调用模型（工具惯性图、离线预算的导航路径）[E1436, E1437]；把重复的控制逻辑长进代码里 [E1438]。

**改善的量（文献陈述）。** 步数 9.1→5.7、token 9.26k→4.94k（AppAgentX）[E1439]；输入 token 43.5×、延迟 5.7–13.4×（AutoDroid-V2，对 AutoDroid）[E1440]；完成时间 −65–70%（AXIS）[E1441]；决策轮数 −78.9%（Act More Decide Less）[E1442]；查询 4.54→1.03（GraphPilot）[E1443]；10.4× 加速（Agent JIT，对 Browser-Use）[E1444]；中位费用 1.9×、延迟 −33.4%（Skim）[E1445]；调用 −15–25%（AutoTool）[E1446]；调用 −76.0–91.8%（Growing Harness）[E1447]。

**分歧（文献陈述）。** 能把"每步决策"去到什么程度：Act More Decide Less 报告直接让策略输出长动作串会坍缩或过度承诺 [E1448]，AutoDroid-V2 却整段生成脚本 [E1433]；Skim 把多数步当机械步、保留 UI 路径，AXIS 直接绕过 UI 走 API [E1437, E1432]。

### F5 每次调用的上下文过长或持续膨胀（12 条）

**怎样陈述问题（文献陈述）。** 每次调用要读的东西太多：网页观察几万到几十万 token、截图历史、逐轮追加工具结果的轨迹。FocusAgent 说网页观察常超过几万 token，撑爆上下文并抬高费用 [E1449]；Prune4Web 说 DOM 有 1 万到 10 万 token [E1450]；AgentDiet 说不断增长的轨迹造成的输入 token 费用被普遍忽视 [E1451]；Complexity Trap 说迭代推理产生又长又贵的上下文历史 [E1452]；TokenPilot 说长会话累积冗长的执行痕迹、抬高每轮推理费用 [E1453]；LineRetriever 说观察经常超过上下文上限 [E1454]。

**归因（文献陈述）。** 原始观察和累积历史又长又多半无关：工具调用及其结果留在轨迹里、被之后每次输入重复读 [E1455]；token 计价加上注意力的二次复杂度，让调用随轨迹增长变得贵而慢 [E1456]；只靠语义相似度检索不够，因为观察是有状态的、带着前面动作的后果 [E1457, E1458]；DOM 超出上下文容量造成截断和注意力稀释 [E1459]；改动提示词的压缩会破坏缓存前缀 [E1460]。

**正式的目标（文献陈述）。** 多数写的是"压缩率 + 成功率"这类指标对：Pruning(o_i) = 1 − |o_r|/|o_i|（FocusAgent、LineRetriever）[E1461, E1462]；Keep% 与归一化的输入/输出 token（AgentDiet）[E1463]；效率—效果前沿（Complexity Trap）[E1464]。TokenPilot 写成优化问题：max_M [Σ_{m∈C'} U(m|C')] / K(C')，C' 是管理后的上下文、U 是消息对后续动作的边际贡献、K 是它的开销 [E1465]。

**解法怎样接上（文献陈述）。** 用小模型或程序挑出观察里有用的部分 [E1466, E1467, E1468]；裁剪轨迹历史（观察遮蔽、反思式删除过期内容）[E1469, E1470]；在压缩时保持字节级相同的前缀以免缓存失效 [E1471]。

**改善的量（文献陈述）。** 观察 −50–80%（FocusAgent）[E1472]、−61–73%（LineRetriever）[E1473]；输入 token −39.9–59.7%、总费用 −21.1–35.9%（AgentDiet）[E1474]；费用减半（观察遮蔽）[E1475]；费用 −56–87%（TokenPilot）[E1476]；候选元素减少 25–50 倍（Prune4Web）[E1477]。

**分歧（文献陈述）。** 要不要再花一次模型调用来决定丢什么：Complexity Trap 说简单遮蔽和模型摘要一样有效 [E1475]，AgentDiet 和 FocusAgent 都靠一个额外模型来判断 [E1470, E1466]。

### F6 环境与工具执行本身成为瓶颈（6 条）

**怎样陈述问题（文献陈述）。** 问题在环境一侧：搜索需要快速的状态检查点与回滚，DeltaBox 说现有机制复制整份状态、要几百毫秒到几秒 [E1478]；TClone 问能不能便宜地叉出一份活的工作区 [E1479]；WebDreamer 说真实网页充满不可逆动作，回溯不可行，过度探索又拖慢用户体验 [E1480, E1481]；ToolCaching 说重复的工具请求没人处理、拖长响应又放大 API 费用 [E1482]；DMI 说面向人的 GUI 迫使模型把高层目标拆成冗长易错的细粒度动作序列、调用次数过多 [E1483]。

**归因（文献陈述）。** 环境不是为 agent 造的：全量复制状态慢、检查点工具是为迁移和备份设计的 [E1484, E1485]；工具调用夹在两段推理之间、远程 API 的执行时间可能主导端到端延迟，而调用有 40% 以上是重复的 [E1486]；命令式 GUI 把"策略"和"机制"耦合在一起，模型不得不发导航链、跑高频的观察—动作循环 [E1487]。

**正式的目标（文献陈述）。** WebDreamer 把任务写成 POMDP 并按模型预测控制选动作 [E1488]；ToolCaching 的缓存价值 v_i = λ1·延迟 + λ2·费用/大小 − λ3·e^(−TTL/τ) [E1489]；DeltaBox 写的是四条设计要求（毫秒级耦合检查点、写放大与改动成比例、O(1) 回滚、对 agent 透明）[E1490]；DMI 报成功案例上的成功率、调用数和时间 [E1491]。

**解法怎样接上（文献陈述）。** 只复制状态的增量（写时复制、O(1) 层切换）[E1492, E1493]；先用模型模拟后果再行动 [E1494]；按语义特征缓存工具结果 [E1495]；把导航与交互变成声明式原语、由系统而非模型执行 [E1496]。

**改善的量（文献陈述）。** 状态管理开销从总时间的 23–48% 降到 1–2%（DeltaBox）[E1497]；叉出 4.9×、端到端 1.9×（TClone）[E1498]；比树搜索快 4–5 倍的墙钟（WebDreamer）[E1499]；端到端延迟 −34%（ToolCaching）[E1500]；调用 8.16→4.61、时间 −39%（DMI）[E1501]。

### F7 重复摸索：跨任务不复用过往执行（28 条）

**怎样陈述问题（文献陈述）。** 同样的工作被反复支付：TraceCompiler 说 agent 反复为已执行过的流程付费、同一意图每次重推同一串工具调用 [E1502]；"Internal APIs" 说网站为浏览器设计，agent 只能反复浏览页面、反推可调用的路由，慢、脆、且在多个 agent 之间重复 [E1503]；MobileGPT 说 LLM 的不可靠和高运行成本限制了实用性 [E1504]；AgentReuse 说生成计划要几十秒，而约 30% 的请求相同或相似 [E1505]；ActionEngine 说反应式循环的延迟和费用随动作数增长，agent 反复重新发现同一个应用怎么用 [E1506]；EchoPath 说对经常性的企业任务，每次都跑一遍新的观察—规划—定位—动作循环是低效的 [E1507]；Metis 说经验存成文字还是代码是设计时定的，取舍不清楚 [E1508]；SpeedRunner 说技能学习的工作把省钱当作事后考虑，不知道哪种技能表示省钱 [E1509]。

**归因（文献陈述）。** 无状态：模型是无状态的，agent 在会话边界丢掉轨迹和反思 [E1510, E1511, E1512]；每次交互都付"发现税"：打开站点、检查 DOM、点、猜、重试、花 token 推理页面状态，而不同 agent 在同一站点各自重推同样的流程 [E1513]；已有的记忆是文字、要另一个模型再规划，不是直接可执行的 [E1514]；自然语言技能让 agent 每次复用都重新阅读和推理同一套流程 [E1515]；复用难，因为轨迹里可复用的流程和偶然细节混在一起、按原始请求文本算相似度会失败、页面会漂移 [E1516, E1517, E1518]。

**正式的目标（文献陈述）。** "Internal APIs" 给出采用条件 f_route < c_rediscovery = c_latency + c_compute + c_tokens + p_fail·c_retry [E1519]；SKILL.nb 写成 (y*,z*) = argmin C_maint + C_run s.t. J_perf ≤ J_perf^ref + ε，即在性能不劣于参考的约束下最小化维护和运行成本 [E1520]；Grounding Agent Memory 用按调用数打折的奖励 r_i = p_i(1 − q_i/B) [E1521]；AgentReuse 把响应延迟拆成计划生成 t_p 和执行 t_e [E1522]；SpeedRunner 把技能库 L 当作策略的参数、由归纳器 g: L×H→L 更新 [E1523]；其余多数无公式（MobileGPT 三条设计目标、Metis 的 token 与轮次、ActionEngine 的成功率/延迟/费用）[E1524, E1525, E1526]。

**解法怎样接上（文献陈述）。** 把轨迹编译成可执行的工作流、脚本或工具，把有证据支持的决策从模型的运行时职责里拿走 [E1527, E1528, E1529]；共享发现的结果（把学到的 API 路由发布到共同维护的图）[E1530]；参数化的任务/子任务记忆，按相似请求召回 [E1531, E1532]；从轨迹蒸馏技能，文字做低成本的暂存层、只把反复出现的稳定计划升成可调用的工具 [E1533, E1534, E1535]；用执行证据决定哪些步骤固化成代码、哪些留给模型 [E1536]；让策展器读环境去核实记忆 [E1537]。

**改善的量（文献陈述）。** 34 次 API 调用编译成 11 次（TraceCompiler，单个意图）[E1538]；热缓存 950 ms 对浏览器 3,404 ms、冷启动 3–5 次回本（Internal APIs）[E1539]；热启动延迟 −62.5%、费用 −68.8%（MobileGPT）[E1540]；延迟 87→27 s、费用 $0.40→$0.05（ActionEngine）[E1541]；执行 token −13.5%/−22.8%（Metis）[E1542]；查询 8.8→4.7、费用 $3.38→$1.68（Grounding Agent Memory）[E1543]；训练过程中费用下降的只有 SpeedRunner 一种 [E1544]。

**分歧（文献陈述）。** 有直接的否定证据：CTIM-Rover 在真实软件工程任务上，跨任务记忆没有胜过基线（40% 对 42%），只用记忆时降到 31% [E1545]；"Are Online Skill and Memory Modules Worth Their Tokens"（放在 F8）在等 token 预算下，不带模块的原始 actor 与 AWM、ASI、ReasoningBank 持平或更好 [E1546]。这两条与本家族多数论文的正向结论相冲突，但它们的设定不同：一个是 SWE、一个是等预算对照。

### F8 改进产物本身抬高运行成本（8 条）

**怎样陈述问题（文献陈述）。** 这是改进循环内部的盲点：ESPO 说 GEPA 这类进化式提示优化器每轮追加规则，提示词无限增长、拖高延迟和 token [E1547]；ClawTrace 说技能蒸馏没有逐步的成本，分不清"补一个缺失步骤"和"删一个昂贵但无用的步骤" [E1548]；"Worth Their Tokens" 说在线记忆和技能模块消耗的 token 很少和 actor 的放在一起报告 [E1549]；SoL-Pi 说任务级 token 效率已是一等的系统问题，此前的效率工作降的是每 token 的价格，它改的是 harness 的用法 [E1550]；SEDM 说记忆无约束增长会抬高推理的费用和上下文 [E1551]。

**归因（文献陈述）。** 学习信号里没有成本项、也没有成本归因：进化式优化器只会追加 [E1552]；蒸馏把技能当整体、把轨迹按成败二分 [E1553]；辅助模块花掉的 token 不能用于任务，而且每一步都把 actor 的提示撑大——"双重成本" [E1554]；harness 里工具、上下文、验证、委派、恢复、终止耦合在一起，局部改动会把费用转移到下游 [E1555]；记忆里的噪声累积、检索和拼上下文的开销随之增长 [E1556]。

**正式的目标（文献陈述）。** SEDM 的写入准入分 S = ΔR − λ_L·ΔL − λ_T·ΔT（奖励差减延迟差减 token 差，配对 A/B 重放；S ≥ η 才写入）[E1557]；SoL-Pi 的两道门：所有能力指标在预定容差内、且至少一个效率指标改善，保留非支配者 [E1558]；ESPO 的目标仍是准确率 p* = argmax E[M(m_p(x), y)]，提示长度和延迟只作报告 [E1559]；"Worth Their Tokens" 无公式，报每任务成功率和跨全部模块合计的 token [E1560]。FRAMES 的双目标 max_S (PR(S), −Cost(S)) 及按类别不回退的约束属于暂缓来源，只在第 8 节描述。

**解法怎样接上（文献陈述）。** 把成本写成共同目标或门 [E1561, E1562]；在轨迹里逐步归因成本并生成剪枝补丁 [E1563]；用结构化诊断代替只会追加的进化 [E1564]；用等预算的对照来评估辅助模块 [E1565]。

**改善的量（文献陈述）。** 提示短 47%、反思 token 约为 GEPA 的 39%（ESPO）[E1566]；去掉剪枝补丁质量回退约增至 2.8 倍（ClawTrace）[E1567]；token 流量 −44.7–49.0%、API 费用约 −1/3（SoL-Pi）[E1568]；比 G-Memory 更准且 token 更少（SEDM）[E1569]。

**分歧（我的判断）。** SEDM 的对照是另一种记忆而非"无记忆的等预算 actor"，"Worth Their Tokens" 的否定结论正是针对后者；两者并不直接矛盾，但说明"记忆省不省"取决于对照选谁。

### F9 构建与改进 agent 的过程本身贵（25 条）

**怎样陈述问题（文献陈述）。** 贵的是改进过程而不是部署后的 agent：GEPA 说 GRPO 这类 RL 通常要几万到几十万次 rollout [E1570]；HarnessLens 说改 harness 要昂贵的验证、并把 harness 演化写成预算约束下的优化 [E1571]；Optimas 说复合系统要端到端重跑才能拿到全局回报 [E1572, E1573]；DreamGym 说在线 RL 的采纳被昂贵的 rollout、稀缺的任务和不可靠的奖励挡住 [E1574]；JudgeFlow 说工作流优化只有粗的端到端信号、不知道该改哪里 [E1575]；Reflexion 说语言 agent 很难快速、高效地从试错中学 [E1576]；Meta Agents 那篇问自动设计什么时候才划算 [E1577]。

**归因（文献陈述）。** 昂贵而稀薄的学习信号：稀疏标量奖励导致样本效率低，rollout（跑一遍系统加评估）在算力、金钱和时间上都贵 [E1578, E1579]；端到端信号给不出归责，搜索会扩展低价值的候选 [E1580]；不同的修改用同一批评测任务验证，很多任务与该修改无关、白跑 [E1581]；系统不可微、配置异质 [E1573]；传统 RL 要大量样本和昂贵的微调 [E1582]；把此前设计过的 agent 全塞进上下文并不比忽略它们更好 [E1583]。

**正式的目标（文献陈述）。** GEPA：argmax E[μ(Φ(x;⟨Π,Θ⟩), m)] s.t. #rollouts ≤ B，Π 是各模块的提示词、B 是 rollout 预算 [E1584]；HarnessLens：H* = argmax E[R(x,τ)] s.t. C(H_0 ⇝ H) ≤ B，C 是从初始 harness 演化到 H 的验证开销 [E1585]；Optimas：v* = argmax E[R(x, f(x;v))]，v 是各组件的联合配置 [E1586]；JudgeFlow：W* = argmax E[φ_eval(a'_M, a)]，W 是逻辑块的组合 [E1587]；Meta Agents：总成本 C_0 + n·C_j 与回本点 n [E1588]；SICA：效用 U = 0.5·p_score + 0.25·(1 − min(1, p_cost/$10)) + 0.25·(1 − min(1, p_time/300 s))，是本文核对到的少数把部署后费用和时间写进选择效用的例子 [E1589]；"Coverage, Not Credit" 用成功—rollout 曲线下面积 [E1590]。

**解法怎样接上（文献陈述）。** 用语言层面的反思代替梯度 RL [E1591, E1592]；给每个修改选它相关的验证任务、减少无关 rollout [E1593]；学一个与全局对齐的局部奖励，让组件各自优化 [E1594]；把 rollout 搬进推理式的经验模型 [E1595]；按块归责、只改最该改的块 [E1596]；让最好的 agent 自己当元 agent 改自己的代码 [E1597]；从大量噪声轨迹里切出因果片段 [E1598]。

**改善的量（文献陈述）。** rollout 少至 35×（GEPA，Qwen3 8B，对 GRPO）[E1599]；留出 pass@1 +7.6–13.6%（HarnessLens，相对值）[E1600]；系统运行次数少于基线（Optimas）[E1601]；0 次真实交互与 8 万次真实交互训练的 GRPO/PPO 相当（DreamGym，作者表述；表中略低）[E1602]；SICA 的 SWE-Bench 50 题子集 17%→53%（第 14 轮峰值，第 15 轮 51%），第 15 轮每题时间略降 [E1603]。

**分歧（文献陈述）。** "Coverage, Not Credit" 是受控的否定结果：按失败归责分配搜索预算，与均匀分配没有可检出的差别 [E1604]；而 JudgeFlow 和 STRACE 把效率归功于更细的归责 [E1605, E1606]。Meta Agents 那篇算出设计出来的 agent 只在两个数据集上按"每个正确回答的费用"胜过人手设计的、回本点约 1.5 万个样本 [E1607]。

### F10 评测与标注成本高昂（9 条）

**怎样陈述问题（文献陈述）。** 拿到判断本身贵：固定规模的基准要么跑多了、要么不可靠 [E1608]；便宜但有偏的代理（LLM 判官）与昂贵的真值（人工审计）如何搭配 [E1609]；机器翻译的人工评测极贵 [E1610]；LLM 标注便宜但常错 [E1611]；agent 的评测要么只看结果、要么要大量人工 [E1612]；让人"审一遍"LLM 的标注会改变标签分布 [E1613]。

**归因（文献陈述）。** 可靠性与成本的张力：按预定样本量跑到底浪费，临时停下又没有保证 [E1614]；代理的偏差未知且随情境变化 [E1615]；标注者的时间花在扫描错误上 [E1616]；全审就没有省钱 [E1617]；只看结果的指标不给中间反馈、而人工评测贵得离谱 [E1618]；锚定偏差 [E1619]。

**正式的目标（文献陈述）。** 序贯检验的停止规则（效力、等价边界、精度、阈值）[E1620]；δ-正确的最佳臂 P(k̂ = k*) ≥ 1 − δ 下最小化 Cost(τ) = c_F·τ + c_Y·Σ A_t（判官与审计各有单价）[E1621]；验证器 P_θ(v | x, ŷ, ê) 挑最可疑的标签送人 [E1622]；与人工共识的一致率 [E1623]。

**解法怎样接上（文献陈述）。** 自适应停止 [E1624]；便宜代理加选择性的昂贵检查 [E1625, E1626]；预填标注 [E1627]；用 agent 评 agent [E1628]。

**改善的量与分歧（文献陈述）。** 样本或审计减少（g013、g060）[E1629, E1630]；每个错误片段的标注时间减半（ESAAI）[E1631]，但 g027 的预注册实验发现 LLM 建议并没有让标注者更快 [E1632]——同一个问题上两个相反的结果；Agent-as-a-Judge 省下 97.7% 的时间和 97.6% 的费用（相对三名人类专家）[E1633]。

### F11 只看结果的评测让效率不可见（13 条）

**怎样陈述问题（文献陈述）。** OSWorld-Human 说计算机使用系统只顾准确率、端到端要几十分钟，实际上不可用，而没有人认真研究过它的延迟 [E1634]；AI Agents That Matter 说评测只看准确率 [E1635]；Cost-of-Pass 说 AI 的推广取决于它创造的价值超过推理费用，而指标只算准确率 [E1636]；"Redundant or Necessary" 提出一个新问题：在成功的轨迹里自动找出低价值的冗余步 [E1637]；Process-Centric Analysis 说结果导向的评测掩盖了反复出现的低效 [E1638]；Efficient Agents 说 agent 的费用膨胀威胁可扩展性 [E1639]；HAL 说评测基础设施慢、费用很少被报告 [E1640]。

**归因（文献陈述）。** 结果中心的评测：反复采样可以无限买准确率，忽略费用就没有上限 [E1641]；价值和费用被分开报告 [E1642]；时间依赖机器配置、所以被拒作指标 [E1643]；轨迹被当线性日志读，低效被遮住 [E1644]；越复杂的架构费用越高、几百次调用一个任务 [E1645]；agent 逐步累积延迟，每步都调用模型且提示很长，还会试错和绕路 [E1646]。

**正式的目标（文献陈述）。** 这一家族贡献的主要就是指标：WES⁺ = (1/n) Σ r_t · t_human/t_agent，用人的步数为参照 [E1647]；cost-of-pass v(m,p) = C_m(p)/R_m(p)，每次成功的期望费用 [E1648, E1649]；准确率—费用的帕累托前沿 [E1650, E1651]；冗余步指示量 Δ_t(τ)（删掉第 t 步任务仍成功）[E1652]；补丁候选数 NPC [E1653]；轨迹图 Graphectory 的节点数与边数 [E1654]。

**解法怎样接上（文献陈述）。** 联合报告准确率与费用、比较简单基线、再联合优化 [E1655, E1656, E1657, E1658]；以人为参照的效率分 [E1659]；过程级的轨迹表示 [E1660]。

**改善的量（文献陈述）。** 多为基准发现而非方法收益：最好的 agent 步数是人的 2.7–4.3 倍 [E1661]；联合优化后可变费用 −41–53%（AI Agents That Matter）[E1662]；费用 $0.398→$0.228、保留 96.7% 性能（Efficient Agents）[E1663]；冗余步检测最好也只有 24.88%（Redundant or Necessary）[E1664]。

**分歧（文献陈述）。** 拿什么代替时间：OSWorld-Human 用相对于人的步数近似延迟 [E1647]，程序修复那篇拒绝时间、改数补丁候选 [E1643, E1665]；Cost-of-Pass 和 Efficient Agents 用每次成功的美元 [E1648, E1649]。

## 3 效率只是"次要"的 246 条：它们陈述的是什么问题（我的判断，家族由分类者给出）

这 246 条记录（core 里 228 条来自第三部分核对库）陈述的问题分十类；效率在其中的角色各不相同：

| 陈述的问题 | 条数 | 效率以什么身份出现 |
|---|---|---|
| 评测的分数、标签或判官不可信 | 13 | 人工或专家评测太贵，是用便宜代理的动机，而代理的有效性正被质疑 |
| 基准没有覆盖真正要紧的场景 | 20 | 费用、token、步数、轮次或墙钟只是成功率旁边的一列 |
| 改进循环本身不可信（过拟合、回退、评估者不可靠） | 23 | 预算是过拟合沿着增长的轴，或是让比较公平的对照量；没有人去最小化它 |
| 运行时的可靠性、安全与故障诊断 | 22 | 报告防护措施的开销只是为了说明它小 |
| 跨回合不学习：记忆、工作流、技能 | 56 | 改权重太贵是非参数学习的理由；上下文窗口限制能塞多少经验；步数减少是复用的副产品 |
| 手工设计：自动优化提示、程序、harness、agent 设计 | 48 | 优化预算是约束，改进过程有开销 |
| 长程交互任务上的能力缺口 | 30 | 搜索或采样的算力是换成功率的代价 |
| 训练 agent 的数据和监督稀缺 | 13 | 采集数据的费用是核心动机（每条轨迹的美元数、零人工） |
| 软件测试与 UI 建模 | 12 | 固定的时间或探索预算 |
| 人对 AI 输出的监督与专家领域工作的自动化 | 9 | 效率收益是引入 AI 的承诺，论文关心它带来的质量代价 |

几个观察：
- 分类者在这 246 条里找出 17 条其实在问题或归因里点名了效率瓶颈、只是目标和收益写的是准确率——例如 IdleSpec 把等待工具时的空闲当作浪费、用投机规划填满它，但目标是准确率 [E1666, E1667]；Compiling Deterministic Structure 把前沿模型的费用写进部署约束、说现有优化器让每个节点都是一次模型调用，收益却只报准确率 [E1668, E1669]。这类工作是"用效率的理由做能力的事"，它们和第 2 节的边界是模糊的。
- 最大的两类（记忆/技能 56 条、自动优化 48 条）几乎就是我们上一份文档（`notes/part3/2026-09-30-self-improvement-survey-mining-zh.md`）读的那批：它们把"改权重太贵""上下文放不下""优化预算有限"当作约束或动机，但陈述的问题是能力。AWM 陈述的是长程任务仍然困难、agent 不从过去的成败里学 [E1670, E1671]；ACE 陈述的是上下文适应的简短偏差和上下文坍塌 [E1672, E1673]；那份综述本身把问题定义为可控的、从经验里演化，成本只出现在评测公式的预算约束里 [E1674, E1675]。
- 有 11 条记录在收益里声称了速度/费用/token/步数的改善，尽管问题不是这样陈述的；另有 35 条只在用词里出现减少某量。这是"没有定义的解法"的一部分（第 6 节）。

## 4 完全不谈效率的 57 条（我的判断）

分六类：接受工作的信号不可信（13）、同一任务多次运行结果不同（9）、程序性合规而非任务完成（10）、测试覆盖的缺口（5）、agent 是静态或手工搭的（15）、失败诊断（5）。它们和加速论文共享的机制有：屏幕分辨率超过模型能处理的范围（ScreenSpot-Pro）、多轮调用加大量文本上下文（DOVER）、把长政策文本塞进上下文（两篇合规论文）、固定的预定动作空间（LearnAct）、观察和工具接口结构不好（Adapting the Interface）。这些机制在加速论文里是费用来源，在这些论文里是能力或合规问题的来源——同一个机制，两种问题定义。

## 5 共同的挑战：文献自己怎么说（文献陈述归纳，判断处标出）

把 11 个家族的"归因"放在一起，指向的机制不多：

1. **模型是无状态的、按 token 计价的、串行的决策者，被放进一个循环里反复调用。** 这一条被四个家族从不同侧面说出：每个原子步骤一次调用（F4）[E1418, E1420]；调用与工具串行、解码等结果 [E1383, E1386]；服务系统把每次调用当独立请求 [E1319, E1322]；agent 在会话边界丢掉一切 [E1511, E1510]。我的判断：这是文献里最接近"agent 加速的根本问题"的表述——不是模型慢，而是模型被当作循环里的一个无状态函数来用。
2. **循环的每一圈都带着越来越长的历史。** 轨迹里的工具结果被之后每次输入重复读 [E1455]；token 计价加二次注意力 [E1456]；上下文逐会话增长压在服务端 [E1340]；每次决策都在增长上下文 [E1422]；记忆无约束增长 [E1556]。
3. **同样的工作被反复支付。** 跨任务：发现税、重复摸索 [E1513, E1516]；跨调用：前缀重算、KV 被丢 [E1319, E1323]；跨 agent：不同 agent 各自重推同样的流程 [E1513]；跨工具：40% 以上的工具调用是重复的 [E1486]。
4. **一刀切的算力投入。** 每一步都用最强模型、最高推理档，尽管多数步是例行的 [E1350, E1352]；agent 既不会用多出来的预算，也不会停 [E1376, E1353]。
5. **环境不是为 agent 造的。** GUI 为人设计、把策略和机制耦合 [E1487, E1411]；检查点工具为迁移和备份设计 [E1485]；不可逆动作让回溯不可行 [E1481]。
6. **改进和评测的过程本身贵，且效率在评测里看不见。** rollout 贵、信号稀薄 [E1578, E1579]；改进产物没有成本项 [E1552, E1554]；评测只看结果，反复采样可以无限买准确率 [E1641]。

**文献之间的不一致（文献陈述）。** (a) 延迟由什么主导：Agent-X 说 prefill 和 decode 都重 [E1338]，ToolSpec 说生成工具调用占 80% [E1339]，SPORK 说工具等待占 16–37% [E1377]，ParaGUI 引用 LMM 推理占 75–94% [E1407]。(b) 记忆和技能模块是否值回 token：等预算对照说不值 [E1546]，SWE 上的跨任务记忆是负结果 [E1545]，而 F7 的多数论文报告正收益。(c) 细粒度归责是否省搜索预算：受控实验说没有可检出的差别 [E1604]，JudgeFlow 和 STRACE 说有 [E1605, E1606]。(d) 人用不用 LLM 预标注更快：两篇相反 [E1631, E1632]。

**三点判断。**

1. **解法确实是从定义推出来的，而且推得很紧。** 说"串行依赖"的家族只产出投机和异步；说"每步一次调用"的家族只产出动作粒度和程序化；说"重复支付"的家族只产出复用。反过来也成立：同一种解法（例如把执行过程变成程序）在 F4 和 F7 各出现一次，分别对应"步内"和"跨任务"两种定义——分类者按归因把 Agent JIT、Skim 放进 F4，把 ActionEngine、TraceCompiler 放进 F7。所以要讲"agent 加速"，先把问题定义讲清楚，解法就跟着出来了；反之，从解法出发会把两个不同的问题混在一起。
2. **两个定义还没有对应的优化方法。** F11 的产出是指标（cost-of-pass、WES、冗余步），F8 的产出主要是记账和门；把"每次成功的费用"或"改进产物的运行成本"当作优化目标去设计循环的工作，本文核对过的文献里只有 SICA 的效用函数和 SoL-Pi 的两道门 [E1589, E1558]，以及暂缓的 FRAMES。

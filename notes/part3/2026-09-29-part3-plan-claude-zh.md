## 1 一页概要

**要做的事（用户要求）。**

- 方向一，全自动的改进循环。现在由人带着编程 agent（Claude Code）做“看轨迹、找问题、找原因、判断属于哪一类、改、重新测试”，目标是让这个循环全自动、不用人。要找的问题包括明显的错误、经常犯的错误，以及最耗时间或费用的步骤。改法包括：改代码；改提示词；agent 用现有 action 往往先失败才能完成的地方，写成一个新 action；无法写成固定代码的地方，保留为每次运行时询问或规划。
- 方向二，从轨迹学环境。很多无谓的消耗来自 agent 没有学习环境的办法。在固定环境里，尝试足够多次，交互关系就能摸清：哪个按钮打开什么，字段有哪些选项。这些信息已经在轨迹里。把它们提取出来，做成更精确的 action，减少无谓的试错，让 agent 更快。
- 判断对错的办法（Edwin 的设想）。规则手册里列了很多具体情境。由模型从规则推出情境（包括边角案例）并生成数据，人简单确认，得到一套标准答案，本稿叫它答案库。按 Edwin 的说法，它只检验对错，不是更新 agent 的机制。

**范围（用户要求）。** 对象是按成文规则填写结构化内容的 agent：报销、各类申请等，不只是报销。SAP Concur 只是一个例子，方案不依赖它。任务模型通过 API 调用，权重不能改。

**五条要点。**

1. 文献结论：在有可靠对错信号的评测里，由模型诊断失败轨迹、自动修改执行框架的循环已有先例，它们报告的是成功率的提高 [E470] [E471]。方向二最接近的先例是 SKILL.nb（研讨会论文）和 Grounding Agent Memory（预印本），它们从任务轨迹学习，检验之后才采用（第 6.1 节）。我的判断：算上改进自身的开销后是否划算，已核对的证据很少，有利和不利的都有（第 9 节问题三）；持续运行的改进循环连同维护开销能否回本，在已核对的文献里没有找到。
2. 文献结论：权重不能改时，执行框架通常靠搜索、生成或编辑来更新，候选改动通过验证才采纳，而不是对它求梯度 [E472] [E473]。强化学习可以用来训练一个单独的编辑模型，任务模型保持不变 [E474] [E475]。
3. 我的判断：整个方案里最不可靠的环节，是判断一个改动对不对。依据见第 5 节：没有外部对错信号时自动改进没有胜过直接采样；模型裁判会把失败判成成功；通过了测试的代码补丁有一部分其实是错的；人复核时最容易漏掉与规则有关的错误。
4. 文献结论：在一项 Windows 办公软件的研究里，用 GPT-5 时，同样的导航知识写进提示词，成功率基本不变，做成可调用的接口后明显提高；用 GPT-5-mini 时，只写进提示词也有小幅提高 [E442] [E476]。这份导航知识来自专门的半自动爬取，不是任务轨迹 [E477] [E478]。我的判断：只靠任务轨迹够不够用，是要检验的问题。
5. 我的判断（检索结果）：在已核对的文献里，没有找到在“按规则填报的网页环境”上测试的自动改进循环。较接近的有三类：在企业类基准上自动演化执行框架的循环，例如 StarHarness（预印本）[E471]；在一个企业网页基准上测试在线技能和记忆模块的工作 [E479]；企业软件基准 WorkArena++ 里的费用管理任务，它是评测任务，不是改进循环 [E480]。另有几项面向受规则约束的企业流程的工作，因为不符合来源规则或还没确认而没有使用。所以这一条只说明检索范围。

**本稿的主要建议。**

1. 第一版不训练任何模型，只改执行框架（我的建议，与 Codex 报告的安排一致；第 3.3 节）。
2. 每个候选改动过两道验收，都在筛选用例上判断：先看正确性，再看开销（我的建议；第 4.5 节）。
3. 答案库分成开发、筛选、最终测试三份，效果只用最终测试用例报告；循环不能修改答案库、评分程序和规则文本（Codex 建议，本稿采纳；第 5.4、5.5 节）。
4. 回本以金额计算、以任务数报告：学习和维护花的钱，要在一个系统变更间隔内预期处理的任务数之内，被执行时省下的钱抵消（我的建议；第 8.3 节）。
5. 研究回答三个问题，分别对应方向一、方向二和整体是否划算（问题的提法取自 Codex；第 9 节）。
6. 循环内部全自动；改动用于真实填报之前，由人审核一次（我的建议；第 10 节）。
7. 工作分四个阶段，前三个阶段有事先定好的停止条件（四个阶段和第一、二阶段的条件是 Codex 建议，本稿采纳；第三阶段的条件是我的建议；第 10 节）。

**第一阶段开始前请 Edwin 决定的事**（第 11 节）：用哪个填报工作流、在哪里跑；“询问或规划”里问的是谁；答案库谁来确认、怎么确认；开销以时间还是费用为主要目标；回本的判断标准。

## 3 权重不能改时，自进化改的是什么

Edwin 的问题：能不能按强化学习的方式来做（他说这是随口想到的）；调用 API 改不了权重，执行框架没有梯度，也没有可以计算的损失函数，自进化的 agent 到底在改什么，学界和业界做到了哪一步。

简短回答（依据见下文）：改的是模型外围的提示词、记忆、工具和控制代码。办法是提出候选改动、验收、保留或回滚。训练意义上的强化学习只能用在另外训练的模型上；也有工作只借用它“多试几次、比较、留下好的”的形式，不训练任何权重。

### 3.1 改什么

文献结论：三篇综述列出的可改对象，既包括模型参数，也包括模型外围的提示词、记忆、工具和控制代码 [E481] [E482] [E483]。我的判断：权重不能改时，能改的是外围部分。

### 3.2 没有梯度，改进怎么发生

文献结论：

- 一篇综述（预印本）指出，执行框架的更新不属于标准的强化学习；它由离散的部件组成，通常靠搜索、生成或编辑来更新，而不是梯度下降 [E472]。对整个执行框架的改进，综述给出的通用做法是：候选改动先过验证（单元测试、回归测试、安全检查），通过才采纳，否则保留旧版本 [E473]。
- 本节引用的几项循环大体是同一个形状。提议模型读轨迹、写出候选改动，见 HarnessFix、AutoSaddler 和 Growing Harness（都是预印本）[E484] [E485] [E486]；候选改动在一组用例上重跑 [E487]；再决定保留或回滚：有的按事先定好的条件 [E488] [E489]，有的在数值条件之外还由一个读试验证据的模型来决定，见 DarwinX（预印本）[E490]。
- 头部公司的官方材料里也用外部检查来评估。OpenAI 的示例用几个评分程序加一个模型裁判给输出打分 [E491]。Anthropic 的 skill-creator 对每个用例带技能和不带技能各跑一次 [E492]。GitHub Copilot 在使用一条记忆之前，按它记录的出处核对 [E440]。

用户要求：答案库只检验对错，不是更新 agent 的机制。

我的判断：执行框架确实没有可以求导的损失函数。循环用的是另一类可以计算的量：答案库上的通过与否，以及实测的时间和费用。它们只用来决定保留还是回滚。改动由分析轨迹得出；循环在开发用例上运行 agent，分析的是这些运行的轨迹；预期答案不交给提议模型。

Codex 建议（本稿采纳，取自交叉核对 C02、C03）：用答案库检验改动后 agent 做得对不对，是 Edwin 的设想；据此决定保留还是回滚，是本稿对这个设想的用法，请 Edwin 在第 11 节第 5 项确认。补充的一点是它的后果：保留还是回滚取决于筛选用例上的判定，所以这些判定会影响最后留下哪个版本；用来报告效果的最终测试用例，不能参与任何一次保留或回滚的决定（第 5.5 节）。如果 Edwin 要求答案库完全不影响留下哪个版本，就要另想筛选的办法，见第 11 节。

### 3.3 强化学习的位置

文献结论：

- 有的工作用强化学习训练任务模型的权重 [E493] [E494]。我的判断：任务模型通过 API 调用时，这条路走不通。
- 有的工作保持任务模型不变，另外训练一个模型。Harness-R1（预印本）训练一个编辑模型来写改动 [E474] [E475]；另有工作训练一个给候选动作打分的模型 [E495]，或一个写反思的模型 [E496]。
- Harness-R1 用到的条件：奖励来自基准自带的评分 [E370]；训练任务上万条 [E371]；用一个更强的模型生成冷启动样例 [E372]；训练用 GPU 节点 [E373]。它的奖励里没有留出任务上的表现，也没有效率项，作者把这两项列为未来工作 [E497]。
- 在它的留出任务协议下（任务模型是一个冻结的开源小模型，三个基准，每个补丁只看十条失败，三个种子），训练过的编辑模型提高了留出任务上的成功率；换成两个没有专门训练的大模型来写改动，一个使成功率下降，另一个的变化与零没有可分辨的差别 [E375]。
- 不训练任何权重、只借用强化学习形式的做法也有：把同一任务的多次运行放在一起比较，用文字总结经验 [E498]；给记忆条目学一个效用分 [E499]。
- 在一项技能优化研究里（预印本，每个设置只跑一次），把整个改进过程交给很强的提议模型自己安排，在多数比较中胜过规定好流程的方法；换成中等的提议模型，在仅有的两个任务上规定流程的方法反而领先 [E434] [E435]。

我的建议：第一版不训练任何模型，先检验对错信号和几种改法是否足以带来改进。是否训练编辑模型由 Edwin 决定（第 11 节）。这是先后顺序上的安排。

### 3.4 学界和业界做到哪一步

文献结论：

- 一篇综述把“完全不需要人参与的自进化”看作目标，不是现状 [E500]。我的判断（采纳 Codex 交叉核对 C13）：它说的是整个生命周期；在实验范围内，自动诊断、修改、筛选的循环已经有系统做到，见下一条。两者说的是不同层次。
- 学界。HarnessFix 的自动诊断和修复在四个基准上提高了任务完成率（一个任务模型）[E470]；StarHarness 在企业类基准的留出任务上有提升 [E471]；DarwinX 在网页环境里改进了执行框架 [E501]。不利的证据见第 5 节和第 9 节问题三。
- 业界。我的判断：在来源规则的范围内，头部公司公开的材料多是评估改动的工具和示例（第 3.2 节）。产品里让 agent 自动积累经验的，核对到 GitHub Copilot 的记忆功能（公开预览，需要开启）：它不经人工逐条审核，靠使用前按出处核对、以及按仓库权限限定谁能产生和使用记忆 [E440] [E502]。GitHub 属于 Microsoft，本稿把它算作头部公司的官方材料；这个归类是否合适请 Edwin 确认。

## 4 方向一：自动改进循环

### 4.1 环节

看轨迹、找问题、找原因并分类、选改法、改、重新测试，这几个环节是用户要求，对应下表第 2 到 6 个环节。第 1 个环节里记录版本、第 5 个环节的“一次只改一处”、第 6 个环节用筛选用例、第 7 个环节的规则，是我的建议。

| 环节 | 做什么 |
|---|---|
| 1 收集 | 记录每次运行的轨迹；同时记录提示词、代码和 action 的版本 |
| 2 找问题 | 明显的错误、高频的错误、最耗时间或费用的步骤 |
| 3 归因和分类 | 找出原因，判断属于哪一类 |
| 4 选改法 | 改代码；改提示词；写新 action；保留为每次运行时询问或规划 |
| 5 改 | 默认一次只改一处，标明改的是哪一类 |
| 6 重跑 | 在筛选用例上重跑改动前后的版本，逐个用例记录结果 |
| 7 验收 | 按第 4.5 节的两道验收决定保留、回滚，或证据不够；记录每个候选改动的结果和它用掉的调用、时间和费用 |

循环分析的轨迹来自两处：开发用例上的运行，以及日常运行。用哪些，见第 11 节。

Codex 建议（本稿采纳）：

- 轨迹里，模型调用、工具调用、环境操作和业务任务分别编号，不用步数或 action 调用数当所有开销的共同单位。
- 提议模型给出的原因是待验证的假设，要附上支持它的轨迹、反例，以及能区分不同原因的检查。“找不到按钮”可能是定位失效，也可能是前置条件没满足。
- 验收的结果有三种：保留、回滚、证据不够。重复运行之间的差别大到无法按第 4.5 节的条件判断时，记为证据不够，补充运行或继续修改后再判断。

### 4.2 找问题：失败之外的浪费

文献结论：

- 失败步骤的定位。HarnessFix 里（一个任务模型，每个基准取二十条失败轨迹，对照人工标注），把轨迹先整理成结构化记录再分析，定位的准确度明显高于直接用原始轨迹 [E358]。
- 成功但步数多的运行。一项工作把每次运行的步数，与多个 agent 合并数据里同一任务最短的成功轨迹比较 [E503]。这里量的是操作次数，不是费用。
- 让模型判断哪一步多余。在一个客服轨迹的基准上，三个模型、三种策略的步骤级得分都很低 [E504]。另一项工作里，模型给出的“是否必要”标签与人工标注有两成左右不一致 [E505]。
- 用确定性规则找绕路。一项工作从完成结果往回追，只保留产生了后来所需事实的步骤 [E506]；TraceCompiler（预印本）只在后一步的参数确实来自前一步的输出时，才认定两步有依赖 [E507]。
- 针对浪费的改动不一定省钱。CostCraft（研讨会论文）从轨迹提炼技能，其中一类改动专门删掉浪费的步骤（一个运行环境、一个模型）。带这个技能时，成功任务的费用中位数仍高于不用技能；迁移到另一个基准后也没有省钱 [E433] [E508]。去掉删步骤的那类改动后，质量变差的任务明显增多；去掉轨迹摘要里按步骤计算的费用后（单个种子），费用增幅和变差的任务都更多 [E433]。
- 分析本身有开销。一项工作在首次尝试之后生成反馈再重试；把生成反馈的 token 也算进去，总 token 多于只做首次尝试，尽管它的通过率在每组里都最高 [E509]。HarnessFix 报告了离线修复用掉的 token [E510]。

我的建议：

- 每一步记录每次模型调用和每次环境操作的起止时刻、提供这次调用的模型、token 和费用。token 按 slides 的五类分开（第 8 节），各按实际单价计 [E511]。有了起止时刻，才能算出被重叠遮住的时间。找“最贵的步骤”先用这些计量排序，不靠模型判断。
- 自动找错误或浪费步骤的程序或模型，在用来驱动改动之前，先对照一小批人工标注量一下准确度 [E505] [E512]。
- 针对浪费的改动，按第 4.5 节的两道验收决定是否保留。循环自己的分析开销记在学习维护账本里，用来判断是否回本（第 8.3 节），不并入单次运行的费用。

### 4.3 选改法：先分类再选改法

用户要求：循环里有“判断属于哪一类”这一环节，再按类别选改法。

文献结论：

- 自动判断该改哪里已经有人做，并且对照人工标注量过定位的准确率和层级判断的得分 [E358] [E484]。也有工作让模型自己选修改层级 [E417]，或要求把修补放在最早能拦住问题的环节 [E513]。
- HarnessFix 的消融里，在同一系统内只改提示词、去掉基于轨迹的诊断、去掉验收检查，三者在四个基准上都低于完整方法；去掉诊断时，修改的依据同时换成了原始轨迹的摘要；所引条目没有说明各变体用掉多少资源 [E356] [E357]。
- 与只改提示词的方法、与通用修改器的跨系统比较也有 [E359] [E415] [E418]。我的判断：这些比较里，系统之间的差别不止一处。其中一项只报告了一次优化，演化和报告用的是同一组任务 [E418]。
- 对“先判断哪个部件该负责，再把改进资源集中到那里”的一项直接检验（预印本），在训练任务池上没有发现可检测的收益，判断错了还有代价 [E514] [E515]。给每个部件留一份最低份额之后，在作者自建的任务池上与平均分配等效；在另一组任务上差别不显著，但没有证明等效 [E515]。它改的是小模型的权重扰动，不是提示词或代码。
- 另一种做法见 HarnessCompass（预印本）：两条轨道并行，一条只许改代码类的部件，一条只许改文字类的部件；在演化任务上通过率高的一条胜出，再由整合模型把另一条里它能判断有帮助的改动并入，胜者超过当前版本才接受 [E516] [E517]。
- 关于给提议模型看什么。一项 2024 年的提示词优化研究里（四个任务，一个目标模型），用假的错误样本代替真的，三个任务上效果相当，一个略低 [E439]。一项文本分类的执行框架优化里，给提议模型看完整的执行轨迹，比只看分数或分数加摘要得到的候选准确率更高；这不是留出任务上的结果 [E419]。我的判断：这一条与 4.2 第一条不矛盾，两者量的是不同的事，一个是定位失败步骤，一个是提出改动，任务领域也不同。

我的建议：第一版按用户要求先分类再选改法，分类表同时用于诊断和报告；每一类改法都保留最低份额的尝试。

Codex 建议（本稿采纳其中的对照组设计）：分类表用人能读懂的类别；另设一个通用修改器对照组，给它同样的原始轨迹、同样的修改权限、同样的验收和同样的资源。Codex 还建议只有分类在相同资源下产生更有效的改动，才保留按类选改法；分类是用户要求的一环，本稿不直接采纳这一条。我的建议：对照组同样好或更好时是否仍保留分类，由 Edwin 决定（第 11 节）。

我的建议：无法写成固定代码的地方，改法是在执行框架里把这一处写成每次运行时询问或规划。这个改动同样要验收。如果“询问”包括问用户：该问的时候问了算对；不该问的时候问了，或该问而没问，都算错。

### 4.4 什么可以写成代码

文献结论：

- Growing Harness 要求提议模型把确定的、可复用的操作写成代码，模型调用留给需要语义判断的地方 [E486]。
- TraceCompiler 在轨迹不足以确定一个不可逆操作的效果时，不生成可执行的流程，改为上报 [E518]。
- 一个生产系统的设计规则是：模型只做信息提取和选择，所有数值计算交给确定性程序 [E519]。
- 一项工作在一个客服基准上把形式化的策略检查接进工具调用，端到端耗时增加，作者归因于操作被拦下之后的重试；授权判断本身很快 [E520]。

我的建议：轨迹能完全确定的部分（字段依赖、算术、格式校验、审批前置条件）可以写成代码；有歧义的选择留给模型；提交这类不可逆操作，轨迹没有完全确定时不写成代码。

### 4.5 验收

文献结论：

- 两项工作的消融里，去掉验收后结果变差。一项在深度搜索基准上，单次运行 [E521]；一项是 GRASP（预印本），在病历系统基准上，三个种子 [E522]。
- 把效率写进保留条件的循环，已核对的文献里例如这两项（都是预印本）。SoL-Pi 要求每个能力指标在事先定好的容忍度内、且至少一项效率指标改善 [E455]。RRSI 只接受得分提升超过噪声的候选，并要求 token 增幅不超过一个随提升而定的上限 [E396]。
- SoL-Pi 在一个基准上（一个模型，单点估计）报告了两个配置：四种机制全开的版本 token 少了近一半，平均分略低于基线；得分最高的单机制配置分数高于基线，但它是从同一基准的表里挑出来的 [E523]。在 RRSI 的一个实例上，各方法最终演化出的执行框架都比初始框架多用 token [E397]。两项报告的开销都是 token 数，不是墙钟时间。
- GRASP 的作者说，验收是稳定性的来源，也是训练期开销的大头 [E524]。另一项工作里，直接构造或修改改动的调用只占总 token 的一小部分，其余是任务执行和候选验证，两者没有分开统计 [E445]。
- 在大模型版本迁移的研究里，总体准确率上升时，仍有一部分原本正确的样本变错 [E525]。另一项研究在自己的迁移数据上也看到这种情况，作者指出只按总体得分验收会放过这些退化 [E526]。

Codex 建议（本稿采纳）：候选改动先过静态检查和局部检查，再到环境里重跑。验收的阈值和统计精度，在小规模试验之后、正式比较之前定下来。

我的建议：验收分两道，都在筛选用例上判断。改动前后在相同的缓存状态下比较：事先选定两边都先用一次不计入比较的运行预热，或两边都从冷缓存开始。

- 第一道看正确性，按用例逐个判断：一个用例在重复运行中每次都对才算通过；没有用例从通过变成不通过。
- 第二道看开销：每次成功的墙钟时间和每次成功的费用，按第 8.2 节第 3 条在全部筛选用例上取总和之比后判断。事先在时间和费用里指定一项为主要目标，并给两项各设一个增幅上限。修正了错误的改动，两项都不超过各自的上限就保留。没有修正错误的改动，主要目标下降、另一项不超过上限才保留。
- 模型调用数、操作数和步数只记录和报告，不作为保留条件。步数随 action 的粗细而变；只加一次调用却同时省了时间和费用的改动，不应被调用数拦下（采纳 Codex 交叉核对 C10）。
- 主要目标选时间还是费用，由 Edwin 决定（第 11 节）。

我的判断：先看能力、再看效率的两道顺序有先例，但 SoL-Pi 按容忍度看能力指标，不逐个用例判断 [E455]；“修正了错误就允许开销有限增加”更接近 RRSI 的规则，不过它看的是总体得分的提升，只给 token 计价 [E396]。把墙钟时间放进保留条件，在已核对的文献里没有找到，需要自己验证。

## 5 判断对错：答案库与验收的可信度

### 5.1 团队的做法

用户要求（Edwin 的设想）：模型读规则手册，推出具体情境并生成数据，人简单确认。例子：规则不允许报销 Airbnb，就做一张带 Airbnb 收据的报销单，看 agent 是照常提交、拒绝，还是发现有事先审批的邮件因而可以报销。

### 5.2 文献里的先例

文献结论。SOPBench 是一个检验 agent 是否遵守操作规程的基准（已列入 EMNLP 2026 主会日程）。LogiSafetyGen（预印本）是把法规文本转成检查条件、再生成参考轨迹的方法，作者用它建了基准 LogiSafetyBench。

| 工作 | 要测哪些情况由谁定 | 模型做什么 | 人做什么 | 证据 |
|---|---|---|---|---|
| SOPBench | 程序按约束条件的组合枚举；为减少重复，失败的“且”条件里只让一个约束不满足，成功的“或”条件里只让一个约束满足 | 为每个指定的组合生成具体数据，再由判定程序自动校验 | 事先设计服务函数、约束和校验程序并写成代码；自动重新生成到预定次数仍不符的数据，由人手工修正；最后逐个复查用例 | [E451] [E467] [E527] [E340] [E398] |
| LogiSafetyGen | 搜索程序生成合规的参考轨迹 | 从法规文本提取候选规则；撰写任务指令 | 全体作者三轮独立审核，一致同意才保留候选规则；再逐条标注用例 | [E343] [E344] [E342] [E528] [E529] |

我的判断：

- 两项里，要测哪些情况都由程序决定；具体数据或任务指令由模型在此之后生成。
- LogiSafetyGen 里模型还从法规文本提取候选规则，这与 Edwin 的设想有一部分相同。在“全体作者三轮审核、一致同意才保留”的标准下，候选规则有四分之一以上未被保留；候选用例在作者标注中也有四分之一以上未被接受 [E528] [E529]。
- Edwin 设想的“模型从规则手册直接推出情境”，在这两项里只有部分对应。本稿只核对了这两项先例。
- 两项都没有用户中途回答问题的设置：SOPBench 的用户请求在开头一次给出，之后只在 agent 停止调用工具时重发用户已知的信息 [E353]；LogiSafetyBench 里被测模型的任务是生成一段程序 [E354]。所以如果“询问”包括问用户，“该问的时候有没有问”要自己设计检查。
- SOPBench 只覆盖能写成代码的前置校验 [E399]；LogiSafetyGen 的规则模板只约束操作的先后顺序，管不到参数取值，例如金额是否在限额内 [E355]。

### 5.3 人工简单确认靠不靠得住

说明：这一节的证据来自表格标注、程序员判断代码断言、主观文本标注、临床计算基准、医生诊断实验和机器翻译的人工评估，没有一项来自按规则填报的用例。

文献结论：

- 在一项表格标注实验里（错误是人为植入的），人复核模型的预标注时，发现率随错误类型差别很大：要理解标注规则才能发现的错误纠正得最少，数字写错纠正得最多 [E530]。
- 在程序员判断模型生成的代码断言的实验里（预印本），错误地接受了错误断言的那些判断，平均用时最短；自信程度与判断对错没有显著关系 [E531] [E532]。
- 在一项主观标注任务里，标注者先看过模型的建议后，所给标签与模型建议的重合明显增加；同一个模型对照这种标注的得分也明显更高 [E533] [E534]。
- 在一个临床计算基准上（预印本），四个模型用原始标注打分，比用重新计算的标注打分低很多。重新计算的标注由同一模型的五个副本多数一致产生，作者把它当作医生标注的替代，只有一小部分经医生复核 [E535] [E536]。

我的建议：

- 盲确认：复核人先看用例和规则条款，自己写出预期结果，再看模型的草稿。依据是上面主观标注任务的结果 [E533]；在已核对的文献里，按规则判断的任务上没有找到直接证据。
- 在待确认的用例里混入一些草稿答案故意写错的用例，偏重规则类和例外类错误，用来量每个复核人能发现多少 [E537] [E538]。
- 同一个用例让不同的模型各起草一次，有分歧的优先交给人。先例只覆盖一部分：临床基准那项工作用同一模型的五个副本，多数一致才采用，不一致的剔除 [E536]；一项机器翻译评估工作的作者指出，辅助人工评估的模型与被评系统基于同一个底层模型时，评估会偏向该系统，并建议用两个不同的模型 [E539]。
- 最终测试用例的标注不看起草模型的答案，并抽一部分做双人复核。

我的判断：这些做法会让确认比 Edwin 设想的“简单确认”多花工夫。是否采用、每批多少条，由 Edwin 决定（第 11 节）。

### 5.4 通过了验收，但其实是错的

说明：这一节的文献结论，前两条来自 agent 的改进循环和记忆模块，其余都来自代码修复和代码生成的研究。

文献结论：

- 在一个命令行基准上（预印本），没有单元测试这类外部对错信号时，执行框架演化没有胜过直接采样；作者的结论是修改执行框架很可能需要可靠的外部对错信号 [E362] [E540]。
- 在一个网页基准的一个站点上，一种记忆模块里被模型裁判标为成功的条目，两个模型下都有一半以上来自按基准评分实际失败的运行 [E541]。
- 已核对的代码修复研究里，做过独立复查的都发现，通过测试的补丁有一部分在复查中不成立，比例差别很大 [E542] [E543] [E544]。
- 2015 年对三种程序修复系统的分析里，通过测试的补丁大多等价于删掉功能 [E545]。同一分析里，一个软件的测试脚本大多只检查退出码，一个修复系统因此接受了大量输出不正确的补丁 [E546]。
- 在一个测试驱动的基准上（一个模型、一套固定的补丁与测试生成流程），对着模型生成的测试再修改一轮后，通过隐藏测试的实例略有增加，但过拟合的比例也上升；修改后新通过的实例，多数没通过隐藏测试 [E547]。
- 在一个基准上（预印本，一个模型，每个实例跑一次），同一个 agent 在同一条轨迹里同时写测试和修复时，两者一起出错的比例接近按相互独立推算的两倍 [E548]。
- 在代码补丁上（两项都是预印本），按每个缺陷要检查的补丁数的中位数，五个过拟合检测工具都没有胜过随机抽查 [E549]；对已通过公开测试的代码，模型监控器在误报率很低时，所测三个验证模型中最强的一个仍漏掉一半左右的隐藏缺陷 [E550]。

我的判断：两个方向都要减少多余的步骤；自动改动有可能把必要的步骤一起删掉，这与代码修复里“删功能”的补丁相似。这是类比，没有在本方案的场景里量过。

我的建议：

- 答案库检查实质内容：字段值、接受还是拒绝、该询问时是否询问；不只检查“报销单提交了”。用例里要有普通填报，不只有边角案例，这样跳过步骤或动辄拒绝的改动会失败。
- 在答案库里加入两类用例，用来检查评分程序本身：故意做错的填报（例如接受了规则禁止的收据），以及本来就办不成的任务。评分程序必须判它们不通过。先例只覆盖一部分：一项工作只保留标准补丁和空补丁都通不过的变异测试 [E551]；另一项工作加强测试后，原本通过的补丁有一部分被判不通过 [E552]。
- 写用例的和写改动的分开：用例在任何改动提出之前写好并确认，不由提议模型来写 [E553] [E548]。
- 在循环之外，对“新通过了原先失败用例”的改动抽样做人工复核，用来量验收的误判率 [E547]。复核不阻塞循环，结果用于第 10 节的决定。

Codex 建议（本稿采纳，取自它的报告和交叉核对 C02；这是方案自己的规则，不是文献结论）：循环的修改权限不包括答案库、评分程序和规则文本；预期答案也不给提议模型看。

### 5.5 答案库怎么分、怎么用

文献结论：

- 在一个家居任务基准上（预印本），不留出、直接在演化用的任务上选版本时，选择时的分数是满分，测试成功率只有三分之二；用严格留出的做法测试成功率几乎相同，差别在于前者的内部分数严重高估 [E447]。DarwinX 在一个终端基准上，循环内部用来筛选的分数升到满分，留出任务上的单次通过率低得多，两个分数的口径不同；最贴合内部分数的版本不是留出任务上最好的 [E554]。
- 一项工作显示（预印本），只看发布版基准可能分不出收益是否来自表面特征：在作者自建的合成账目基准上（一个模型），按表面特征做平衡后，作者按缩减预算复现的一种对比方法增益大部分消失，作者自己的方法增益反而变大 [E555]。
- 在一项用排行榜记录做的模拟里，得分很接近的两个模型，提前停止通常不会触发，要用完整个数据集 [E556]。
- 为了限制留出数据被反复读取带来的偏差，一种方法只在训练集与留出集上的结果相差超过阈值时才返回留出集上的结果，并且加噪声 [E557]；另一种只在新提交显著优于此前最好成绩时才公布新分数 [E558]。

Codex 建议（本稿采纳）：

- 答案库分成三份：循环在开发用例上运行和诊断；筛选用例决定保留哪个版本；最终测试用例在方案和版本都选定之后才用。学习曲线用事先冻结的检查点，在结束后统一测。
- 泛化分层次。同一模板换参数，只能支持“换实例也行”。要声称学会了新流程或新的规则组合，就要专门留出这样的用例。日志、规则推出的用例和测试任务之间，要检查有没有共用答案、对象或几乎相同的执行路径。

我的建议：

- 验收用成对比较：同一个用例，改动前后用相同的重复次数各跑若干次 [E559] [E560]。要分辨多大的改进，事先定好。
- 对已确认的用例做“换表面”的变体：换商户、日期、金额，规则结果不变。改进在变体上消失的改动不保留。先例见上面那项合成账目基准的工作 [E555]。
- 答案库要多大，由团队想分辨的最小改进决定；已核对的文献给不出适用于本场景的数。

### 5.6 怎么评分

文献结论：在五个网页基准、四个 agent 的轨迹上，基准自带的规则评分会把不少有效的运行判为失败 [E346]；十二个模型裁判对“成功”的精确率都不高，会把失败的运行判为成功 [E345]。

我的建议：评分用程序核对最终结果。先核对处理方式（提交、拒绝、询问），再逐字段比对。每个用例重复跑，同时报告“每次都对”的比例。

Codex 建议（本稿采纳）：抽样人工核对判为成功、判为失败和有争议的运行，并报告评分误差对结论的影响。指标除了正确完成率，还包括关键规则的符合率、必要询问和人工接管的次数。

## 6 方向二：从轨迹学环境

### 6.1 最接近的工作

附录 B 按“知识从哪里来、在什么平台上、学成什么、采用前检验什么”列出了最接近的工作。与本方案关系最大的是三点。

文献结论：

- 从任务轨迹学习、并在采用前有检验步骤的，已有 SKILL.nb（研讨会论文）和 Grounding Agent Memory（预印本）。SKILL.nb 的更新通过离线验证才进入技能库，运行时每一步再检查门控条件，不满足就退回文字步骤 [E561] [E423]。Grounding Agent Memory 在整理记忆时，用只读操作去环境里核实没把握的条目，再由整理记忆的 agent 自己决定新建、修改、收窄还是删除；它拿得到任务的评分 [E441] [E562] [E563]。
- 多数工作采用前的检验偏弱，或由模型自己判断。SkillWeaver（预印本）的“通过验证”指调用时不抛异常，作者报告这让屏蔽了异常的坏函数也被标为通过 [E381]。WALT 的测试输入取自构建工具时的演示轨迹 [E378]。ASI 在同一个查询上重跑，由模型裁判判断是否完成，不用标准答案 [E564] [E411]。WebXSkill（预印本）把技能在测试环境里跑一遍，跑不通的丢弃，文中没有说明是否检查任务完成 [E565]。AppAgentX（预印本）是否生成快捷动作由模型判断，论文没有描述生成之后的保留或淘汰 [E385] [E386]。SpeedRunner（预印本）不回放任务，技能更新是否采用也不看留出运行的结果，回归检查交给改写技能库的 agent 自己做；它的留出测试集只用来报告 [E391] [E329]。
- 环境知识不只有环境模型一种形式。条件规则 [E566]、按情境取用的指导 [E567]、状态机 [E382]、带门控的可执行步骤 [E423] 都有人做。也有工作训练一个预测“操作之后页面会怎么变”的小模型，用来在执行前比较候选操作；训练数据是在同一环境里专门收集的交互 [E568] [E569] [E570]。

我的判断：“从任务轨迹学习，检验之后才采用”已经有工作做到。方向二要检验的，是其中在已核对的文献里没有找到直接对应的部分（第 9 节问题二）；这只说明检索范围。

### 6.2 只靠任务轨迹够不够

文献结论：

- 已核对的环境模型工作里，ActionEngine（预印本）和 WebNavigator 的模型来自专门的爬取 [E382] [E571]；MobileGPT 用随机探索加用户操作记录 [E449]。从已有轨迹建页面图或快捷动作的，核对到的有 PG-Agent 和 AppAgentX [E572] [E573]；AgentRR（预印本）也把记录下来的轨迹整理成可以回放的经验 [E574]。
- 在 WebArena 上（一个模型，每个任务跑一次），ActionEngine 直接用爬取得到的状态机时，成功率明显低于预热之后。预热是按评测任务的模板各生成一个任务来跑，由修复模块把发现的问题写回状态机；评测时修复模块关闭 [E384] [E383]。我的判断：在这个评测里，只靠爬取建的模型不如经过预热修正的模型；预热和评测出自同一批模板，这个结果只说明同模板下换实例的情况。
- 在十个手机应用上，先让参与者以“找全功能”为目标做人工探索，再用这些记录给爬虫开路再爬，发现的不同界面比只做人工探索更多；只用爬虫、不用人工记录，比这种混合方式覆盖更少，作者主要归因于登录墙这类需要人输入的界面 [E575] [E576] [E577]。
- 按一项工作的计算（不是实测），要有把握至少见到一次出现率很低的分支，需要几百次运行 [E578]。
- TraceCompiler 从三个实例的轨迹编译出一个收款请求的工作流，每次留出一个实例来测试；评测的是编译出的骨架加手写的参数解析。留出实例需要的分支在另两个实例里出现过时，状态测试全部通过；没出现过时，工作流停下来上报，状态测试只过了一项 [E579]。
- 有一种方法从已有日志估计“再加新轨迹也不会改变某个挖掘算法的输出”的概率，作者用它达到阈值作为停止加轨迹的条件 [E580] [E581]。它假设轨迹是随机独立抽取的；作者指出，按某种策略生成的轨迹可能不满足这一点 [E582]。
- 在一个手机基准上，PG-Agent 把从已有轨迹建的页面图检索出来放进提示词，总体的操作匹配得分只高一点，其中一个场景反而更低 [E583]。

Codex 建议（本稿采纳）：

- 第二阶段（第 10 节）提取知识时先只用任务运行产生的轨迹，不做专门探索。这样可以单独检验轨迹的价值。验证由此做成的 action 仍然要在环境里跑，这部分开销记在学习维护账本里。
- 如果覆盖不足，在后面的阶段加少量定向探索，它的开销在学习维护账本里单列一行。补采数据之后的效果，不能再归到“只用任务轨迹”名下。

我的建议：轨迹随任务运行不断增加，同时记录增长曲线：每加一条轨迹，新增多少页面、跳转和选项，用来判断何时够用。探索只在不会产生真实填报的环境里做。

### 6.3 环境知识要记什么

Codex 建议（本稿采纳）：区分“实际观察”和“归纳规则”。“这些轨迹里选了某类费用后出现了某字段”是观察；“这类费用总需要该字段”是待验证的规则。每条知识记录出处、已知的账号或会话条件、应用版本、支持实例和反例。没观察到的条件保留为未知，不补成看似完整的模型。显式的环境模型不是前提：带条件的记录和 action 的约定够用，就不建环境模型。

文献结论：

- 两个页面算不算同一个状态。在九个网页应用、短时间爬取的实验里，通用阈值得到的模型质量最差，按应用在标注数据上调出来的阈值明显更好；作者认为通用阈值可能不可行 [E584] [E585] [E586]。只是功能重复的页面，这项研究比较的十种算法都识别不出 [E587] [E588]。
- 已有的页面归并规则。一个手机界面数据集先比截图，差异超过阈值时再比较控件标识的集合，并在一千多对界面上量过误判率 [E589]；ActionEngine 由模型识别页面模板 [E590]；MobileGPT 把可做的子任务相同的屏幕算作同一个节点 [E591]。
- 字段的取值限制。在三十个表单的测试生成实验里（一个模型），约束通常第一轮就稳定下来；去掉提交后的反馈，通过率下降 [E592] [E593]。作者在局限里提到，网站的反馈不够详细时，方法可能推不出所需的约束 [E594]。
- 条件字段。一项工作通过比较操作前后表单的差异来枚举表单状态 [E595]；在它的实验里（用 GPT-4o 生成时），动态表单上生成的测试通过率低于简单表单，真实表单上的字段覆盖率不到一半 [E596]。

我的建议：判断两个页面是不是同一个页面，用页面模板和控件标识，不用内容相似度；上面的归并规则是相近的做法，它们在填报系统上是否适用要自己验证。每次访问时把可见的选项列表存下来。我的判断：已核对的文献里，有工作在测试生成中保存操作后出现的表单状态 [E595]；把“字段有哪些选项、什么条件下出现”作为 agent 的长期知识保存并复用的，没有核对到。

### 6.4 以什么形式交给 agent

文献结论：

- 在一项 Windows 办公软件的研究里（两个模型），同样的导航知识做成可调用的接口，比只写进提示词效果更好，见第 1 节第 4 条 [E442] [E476]。代价是每个应用要几小时的自动处理加一天多的人工（作者假设操作者熟悉该软件），而且绑定在一个软件版本上 [E597]。
- 在一个网页基准的子集上（一个模型，每个任务跑几次没有说明），WebXSkill 把从合成轨迹提取的技能做成可调用的工具，成功率在同表以该模型为骨干的各行中最高，高于同一方法只给文字和代码指导的方式 [E598] [E599]。
- 在一个基准上（预印本，三种命令行 agent 配置），agent 做任务前自己写、直接使用的技能，通过率都低于不用技能 [E443] [E600]；在一个网页基准上，写完即用、不经修复的自写技能也低于不用技能 [E601]。
- 在一个小型网页基准上，完整的 ContractSkill（预印本；约定加失败定位加受限修复）明显好于只改写文字的对照 [E437]。
- 在 Mind2Web 上（一个模型），Agent Workflow Memory 把工作流封装成可直接执行的高层动作的变体，只在少部分任务中被调用；与只把工作流放进提示词相比，单步成功率略高，任务成功率没有提高，两者的任务成功率都很低 [E325]。作者举的一个失败例子是订机票时弹出的机场选项：固定的动作序列看不到中间状态 [E602]。

Codex 建议（本稿采纳）：一个 action 有输入参数、适用条件、执行过程、预期效果和异常出口，本稿把这五项叫作 action 的约定。金额、对象编号、当前可选项这类动态数据不写死，存的是读取方法。条件不满足、控件变了、执行后没有预期效果时，action 返回失败位置和当前页面，交回 agent 处理。

我的建议：由环境知识做成的 action 当作候选改动，走第 4.5 节的验收。

### 6.5 学到的东西能用多久

文献结论：

- 在一个代码托管平台的真实版本升级里（一个模型），SKILL.nb 沿用旧版本上学到的内容，与从头开始基本持平；同一测试里其他方法明显下降 [E425]。
- 在终端和数理问答任务上（预印本），按一个模型自动演化出来的执行框架换到另一个模型，收益在一组测试里变负；这组结果每个设置只评测一次 [E603]。在一个代码修复基准上，HarnessCompass 换模型后总体仍有收益，个别代码库下降 [E604]。
- 在代码库技能文档的维护上（预印本），即使把官方的版本补丁交给模型，识别过时内容的得分最好也不到七成；维护后的技能没有在下游任务上重跑 [E605] [E606] [E607]。
- 回放前先检查上次记录的目标元素所在区域的内容有没有变、变了就作废这条缓存，是已有的设计，见 MobiAgent（预印本）[E608]。AgentRR 用检查函数拒绝与已记录顺序不符的调用，只给了一个案例 [E609]。这两项都没有报告检查的误报率和漏报率。

我的建议：

- 每个学到的 action 在执行前做一次便宜的检查。检查要在操作执行之前触发，因为填报系统里有些操作不能撤销。
- 环境知识用最不容易随界面改版而变的信息来描述，例如字段标签和页面模板；屏幕坐标和原始的元素定位串不进长期知识。
- 系统发布新版本、换模型，都当作一次需要重新验收的事件：固定模型版本；切换前在筛选用例上逐个用例重跑，按第 4.5 节决定。最终测试用例只在报告效果时使用。

## 7 循环在哪里跑

用户要求：SAP Concur 只是例子，不需要专门为它搭测试环境。

我的判断：循环要把同一个用例在改动前后各跑若干遍，所以需要一个能重复运行、跑完能清理的环境。起点是团队现在运行 agent 的环境。

文献结论：已核对的文献里没有关于 SAP Concur 测试环境的内容。两个可参考的做法来自别的平台。

- 企业软件基准 WorkArena++（全部任务都在 ServiceNow 平台上 [E610]；第 1 节第 5 条提到的费用管理任务也在其中）在由安装程序统一配置的实例上运行。每个任务用一个新建的用户账号，结束后自动删除，使 agent 的改动不影响后面的任务；评分程序检查数据库和当前页面 [E611] [E612]。被 agent 改过的业务记录是否恢复，所引条目没有说明。
- 基准 REAL 用十一个网站的确定性复制品。操作类任务按开始和结束时的状态比对评分；信息检索类任务由模型裁判按评分细则判 [E613] [E614] [E615]。它还包含故意办不成的任务，看 agent 会不会如实报告办不成 [E616]。作者不保证复制品与真实网站一致，也没有量过一致程度 [E617]。

我的建议：先由团队完成准备工作，再在团队现有的环境里重跑和清理。能建测试身份就用“真实系统”；不允许重复提交就用“停在提交之前”。“复制品”和“两层”要另建一个测试环境，超出了“不专门搭测试环境”的要求，只作备选，是否采用由 Edwin 决定（第 11 节）。

准备工作：由团队在自己的环境里确认有没有测试账号，怎么清理，哪些操作不能撤销，系统自带的检查（例如重复报销检查）会不会让同一个用例第二次跑出不同结果。这些是团队所用系统的事实，由团队自己确认，不作为文献证据引用。

| 做法 | 内容 | 风险 |
|---|---|---|
| 真实系统 | 每次运行用独立的身份，记录里带唯一标记，评分读回保存后的状态 | 取决于系统是否允许建和删测试身份 |
| 停在提交之前 | agent 填完但不做最终提交，按处理方式和已填内容评分 | 学不到提交之后的页面和系统的反馈 |
| 复制品（备选） | 做一个确定性的复制品，每次运行前重置 | 要另建环境；复制品会漏掉不知道的检查；系统更新后会过时 |
| 两层（备选） | 开发迭代在复制品上；确认和最终测试在真实系统上；记录两边逐个用例是否一致 | 要另建环境；还需要“真实系统”至少能跑少量用例 |

## 8 与第一、二部分 Time、Money 公式的关系

第一部分的公式（第二部分沿用）描述一个既定的设计 m（模型加执行框架）在任务 p 上一次尝试的时间和费用，以及除以成功率之后每次成功的时间和费用。它是 slides 从文献改编的分析表达，来源见 slides 的附录 A0。本方案研究怎样把 m 改得更好。先变的是 m，然后才看公式里哪些项跟着变（Codex 建议）。

$$T_{\mathrm{attempt}}=\sum_{i=0}^{N}(D_i+E_i)-T_{\mathrm{saving}},\qquad D_i=\sum_{j=1}^{J_i}\ell_{ij}$$

$$c_m(p)=\sum_{i=0}^{N}\sum_{j=1}^{J_i}\sum_{\kappa\in K}n^{\kappa}_{ij}c_\kappa(\mu_{ij})+x_{\mathrm{env}}c_{\mathrm{env}}$$

$$T_{\mathrm{success}}(m,p)=\frac{\mathbb{E}[T_{\mathrm{attempt}}]}{R_m(p)},\qquad v(m,p)=\frac{C_m(p)}{R_m(p)}$$

符号，按 slides 的定义：

- T_attempt 是一次尝试的墙钟时间。N 是步数。i = 0 放不属于任何一步的调用，例如开头的规划。
- J_i 是第 i 步的模型调用数，ℓ_ij 是其中第 j 次调用的耗时。D_i 是第 i 步的模型时间。E_i 是这一步其余的全部时间：观察、操作、等待、执行框架的间隙、限流后的退避。D_i 和 E_i 都是时长相加。
- T_saving 是因为同时进行而被遮住的时间；严格串行时为 0。
- c_m(p) 是一次尝试的费用。每次调用的 token 分五类：缓存命中、两种时长的缓存写入、未缓存的输入、输出。n 是某一类的 token 数，c_κ(μ_ij) 是提供这次调用的模型在这一类上的单价。x_env c_env 是按用量计费的环境。
- R_m(p) 是一次尝试成功的概率。C_m(p) 是一次尝试的期望费用，对全部尝试取，包括失败的。T_success 和 v 是每次成功的时间和费用。slides 的目标是在成功率不低于下限 R_0 的条件下，同时压低这两个量。

### 8.1 改动影响哪些项

Codex 建议：表的结构和“可能变化的项”一列取自它的报告。我的建议：“同时带来的开销”一列、第一行和最后一行，由我按审阅意见补入。

| 改动 | 可能变化的项 | 同时带来的开销 |
|---|---|---|
| 修正处理结果的错误（字段值、接受或拒绝、该询问没询问） | 成功率上升，每次成功的时间和费用经分母下降；步数和调用数可能不变或上升 | 新增的核对步或询问，计入所在步的调用和非模型时间 |
| 修提示词、代码或流程，少走错路 | 步数下降：被删掉的步连同其中的调用和等待一起消失，之后每一步的提示词也少了这一步追加的内容。成功率可升可降 | 提示词变长；提示词前面的部分一改，之后的首批调用由缓存命中变成缓存写入 |
| 把已知操作交给 action | 由模型调用的 action 一次完成原来几步的操作：步数下降，被并掉的步的调用和观察一起消失（slides 第二部分“步数”一页）。整段不经模型、由代码执行或回放时，这些步的调用数为零（“每步的调用数”一页）。操作和页面等待仍在非模型时间里 | action 内部如果调用模型，这些调用照常计入；执行前的条件检查；action 的说明进入每次调用的提示词，action 清单一改，之后的首批调用变成缓存写入；回退时，已执行的操作和恢复用的额外步数；回退之后仍失败时成功率下降 |
| 用环境知识避免试探 | 被避免的试探步整步消失 | 知识写进提示词时提示词变长；执行时的条件检查；检索如果调用模型，计入调用和费用；用错了知识时成功率下降 |
| 用结构化结果代替重读整页 | 本步和之后各步读入的 token 下降 | 由模型生成结构化结果时多一次调用，而且这次调用要读整页；丢了信息时成功率下降 |
| 保留为每次运行时询问或规划 | 规划的调用计入 i = 0 或所在的步。如果询问的是用户，等回复的时间按 slides 的定义计入非模型时间，一次尝试变长 | 实验里用户的回复由程序模拟，回复时延事先固定并声明；墙钟时间同时报告含和不含等待用户的两个值，第二道验收用不含等待的值。用户回答问题的时间单列为人工小时 |

Codex 建议（本稿采纳）：本方案不直接改变的项也要写明。任务模型和服务档位不变时，token 单价和每个输出 token 的耗时不变；没有专门改调度时，不主张并发带来更多的时间抵扣。方案不必覆盖公式里的每一项。

我的建议：每次尝试结束时，系统自己判断成败的检查（读回保存后的状态、按规则核对，必要时加一次模型调用）是本方案新增的执行开销，时间和费用都计入这次尝试。当前系统一侧也要计入它发现失败的开销，两边的每次成功费用才是同一口径。部署时没有答案库，这个检查怎么做，在第一阶段定下来；它漏判的失败要单独报告。

### 8.2 记账规则

我的建议（在 Codex 建议的基础上补全）：

1. 同一笔节省只记一次。每个改动的节省，只按改动前后在同一组用例上的实测总量之差记一次；第 8.1 节表里各项只用来解释这笔差额，不分别估算再相加。例如 action 把几步并成一步并返回紧凑结果时，“少了中间调用”和“之后各步读入的 token 下降”里有同一批输入 token。
2. 比较调用和操作的数量时，用不随 action 粗细变化的计数：模型调用总数（包括 action 内部的）、操作数。步数只作描述。
3. 每次成功的费用，用全部尝试（包括失败的）的实测总费用除以成功数；每次成功的时间同样用全部尝试的墙钟时间之和除以成功数。实验里每个用例跑相同的次数，多个任务时取总和之比，这样与 slides 的口径一致。研究阶段的成功数按答案库判定；部署阶段按系统自己的成败检查判定，并单独报告它的漏判。这个量假设失败后可以独立地重试到成功；成功数为零时记为无穷大（取自 slides 公式的来源文件）。填报系统里失败的尝试可能已经提交，重试不是没有代价的，这一点要在报告里写明。
4. 删掉一个调用，省下的只是它没有与其他调用、工具执行或页面等待重叠的那部分时间。时间收益以实测的墙钟时间为准；各步模型时间和非模型时间之和只用于诊断时间花在哪里。
5. 版本切换后，部署运行里多出的缓存写入计入部署执行账本；验收和回归重跑里的缓存写入计入学习维护账本。
6. 公式里 i = 0 只放本次尝试之内、不属于任何一步的调用，例如开头的规划、一次性检索。学习的开销不进 i = 0，记在学习维护账本；放进 i = 0 会把建设费除以成功率，并与 slides 附录 B8 的建设费分摊重复。（仓库里另一份文件有不同的写法，已记为 D321，见修订记录。）

### 8.3 三个账本

Codex 建议（本稿采纳三个账本的划分），边界由我补全。每一项开销只进一个账本：

| 账本 | 记什么 |
|---|---|
| 部署执行 | 为处理业务任务本身而发生的运行，不论由哪个版本产生、成功与否：真实部署中的运行，以及研究阶段各组处理任务流的运行（标为模拟部署，与真实部署分开汇总）。包括失败的尝试和之后的重试、action 的条件检查、结果读回、系统自己判断成败的检查 |
| 学习维护 | 只为产生、筛选或维护某个版本而发生的开销：轨迹分析、生成、探索（单列一行）、候选验证、回归、候选版本在真实任务上的试跑（结果不被采用）、构造开发和筛选用例、检测器准确度的人工标注、改动上线前的人工审核 |
| 研究测评 | 只为比较各组或对外报告而发生的开销：最终测试、构造最终测试用例、评分程序的抽检、对新通过改动的抽样复核、专门的审核用例（第 10 节）、测量现有系统的时间和费用构成、额外的消融 |

- 每个实验组（当前系统、各对照组、完整方案）各有一套三个账本。
- 部署运行的轨迹被循环拿去学习时，运行本身只记在部署执行，学习维护只记分析和之后的开销。
- 同一个用例不能既用于验收又用于最终测试。答案库的构造和确认费用按三份用例的条数分摊。
- 几个账本共用的一次性设施（评分程序、测试环境的准备、轨迹记录）按事先声明的份额拆分。
- 人工小时按同样的规则分到三个账本，单独列出，不折成金额（Codex 建议）。

回本。我的建议：沿用 slides 附录 B8 的形式。B8 给的是一次性建设的情形：建设费摊到 n 个任务上，加上每次成功的费用；它假设每个任务重试到成功，所以每任务的费用等于每次成功的费用；相对一个基线，任务数超过“建设费除以每任务节省”就回本。本方案把它扩展为沿任务流累计：到第 n 个任务为止，学习维护账本累计的金额，不超过这 n 个任务上“当前系统每次成功的费用减去所用版本每次成功的费用”之和（所用版本每次成功的费用按不含切换后多出的缓存写入的实测值计），再减去这期间各次版本切换多出的缓存写入。

- 单位。回本以金额计算、以任务数报告。事先声明两次系统变更之间的间隔，以及这个间隔内预期处理的任务数。判断标准是回本任务数不超过这个预期任务数。
- 成功率下限优先。新版本和当前系统的成功率都不低于下限时，才作回本判断；新版本不比当前系统便宜就永不回本。当前系统低于下限而新版本达到时，不作回本判断，单独报告为达到下限所花的学习维护金额和人工小时。
- 失败的任务不能重试、要转交人工处理时，每任务的费用不再等于每次成功的费用，要改用每任务的费用加人工处理的开销，并注明。
- 研究阶段没有真实填报时，每次成功的费用取实测值，任务数取事先声明的预期量，并注明是估算。
- 人工小时与回本任务数并列报告。
- 用户等待的改善，按每次尝试和每次成功的墙钟时间报告，不与离线改进的耗时相抵（Codex 建议）。
- 后台学习另记墙钟时长，因为它决定一项改进什么时候开始生效。

## 9 研究问题与对照实验

下面三个问题分别对应方向一、方向二和整体是否划算。问题的提法取自 Codex 的报告（Codex 建议），本稿按文献核对的结果缩小了范围。每个问题都设计成实验可以给出否定的回答。各问题下“没有找到直接对应”的清单只说明检索范围，不作为新颖性的依据。

**问题一（方向一）：先分类、再按类别选改法，是否有价值。**

- 已有人做过的：自动判断该改哪里，并对照人工标注量过准确度 [E358]。HarnessFix 在同一系统内去掉基于轨迹的诊断，四个基准上都低于完整方法，但同时换了修改的依据；所引条目没有说明各变体用掉多少资源 [E356]。与只改提示词的方法、与通用修改器的跨系统比较 [E359] [E415] [E418]。对“先归因、再集中资源”的一项直接检验没有发现可检测的收益，它改的是小模型的权重扰动 [E514] [E515]。按费用归因的有无，CostCraft 做过单种子的消融 [E433]。
- 在已核对的文献里没有找到直接对应的：在相同且报告出来的改进资源下，只开关“分类并按类别选改法”这一环节的比较；改法同时包括新 action、环境知识和留给运行时询问或规划这三类的循环（只新增或改写 action 的循环已有，例如 [E410] [E618]）；按实际耗时排序的诊断。
- 拆成两问（Codex 建议：开关诊断模块，以及保留相同诊断、只去掉成本优先级；“故意分错”一组和两种提议模型各做一遍是我的建议）。1a：“先分类、再按类别选改法”这一环节开、关、故意分错三种情况比较。1b：同样的诊断，有和没有“按耗时和费用排序、并读成功但昂贵的轨迹”。
- 我的判断：1b 要比的基线，是只看得分也能顺带缩短轨迹的循环。StarHarness 的演化只以基准得分为目标 [E368]，在一个企业基准上（一个模型，统计包含演化用的任务），演化后的执行框架在提高成功率的同时，把每个任务的轮数和工具调用都减少了近一半 [E369]。
- 我的建议：至少用两种提议模型各做一遍。一项工作里，提议模型的能力改变了两种方法的优劣 [E435]；Harness-R1 的实验里，换用两个没有专门训练的大模型来写改动，留出任务上没有收益 [E375]。

**问题二（方向二）：带出处和条件的环境知识，是否值得维护。**

- 已有人做过的：带触发条件和前置条件的记忆条目，对象是客服政策 [E431] [E432]；整理记忆时用环境探测核实 [E441] [E426]；带门控的代码加文字回退 [E423]；单独从任务轨迹学习（第 6.1 节）；一次性建设开销与每任务节省的对比，只计离线爬取的费用 [E332]。
- 在已核对的文献里没有找到直接对应的：同一批轨迹上三组对照（文字经验组、直接技能组、环境知识组；环境知识组的每条知识带出处和条件）；把“错误复用”定义成指标；把“未知”作为知识的一个字段；以及“知识只来自任务轨迹、持续维护的开销与运行节省对齐比较”的组合。
- 我的建议：先定义指标。错误复用：知识或 action 被调用后，事后发现适用条件不成立，或执行后的检查失败。无效往返：被撤销的操作数，加上重复访问同一页面的次数。然后拆成两问。2a：知识的形式不变，只比较加不加出处、条件和未知字段，看错误复用和无效往返是否减少。2b：在金额对齐的条件下，比较环境知识组与文字经验组、直接技能组。
- Codex 建议（本稿采纳）：直接技能组要保留同样的验收和回退。我的判断：一项基准上，agent 自己生成、直接使用的技能低于不用技能 [E443]；不加验收时，这一组可能只是弱基线。

**问题三：算上改进自身的开销后，是否划算。**

- 已有人做过的，有利的：一次性离线建设有回本点的报告。ActionEngine 的比较对象是另一个 agent，只计离线爬取的费用，没有计入预热修正的开销，费用的构成论文没有说明 [E332]；WALT 的正式版按示例价格折算了每个工具的建设费用和回本所需的使用次数，只针对一个基准 [E333]。
- 已有人做过的，不利的：在为问答任务自动设计 agent 的研究里，计入设计成本后，只有少数设置要在处理大量样例之后才回本，其余设置不回本 [E334]。在一个网页基准上（三个模型），与三种在线技能和记忆模块相比，放宽步数上限并加了不调用模型的页面裁剪的普通 agent 成功率最高；预算只按步数上限近似对齐，作者说明结论只针对在线模块 [E428] [E429] [E430]。在一个命令行基准的留出任务上，即使演化时用单元测试作对错信号，演化出的执行框架也只比初始框架略好，两个模型中一个没有变化；这个比较没有计入演化的开销，作者提醒这个基准可能对执行框架不敏感 [E421] [E619]。
- 已有人做过的，其他：SpeedRunner 按训练进度、在固定的留出测试集上报告每条轨迹的成本，把技能归纳的调用按批次摊入；论文对这一成本是输出 token 还是金额前后说法不一 [E331] [E328] [E329]。SKILL.nb 报告了任务流里每次成功的维护 token [E424] 和版本升级后的比较 [E425]。两项工作把构造或修改改动的调用与任务运行分开计 token，但候选验证的运行记在任务运行一边 [E445] [E446]。
- 在已核对的文献里没有找到同时做到以下几点的工作：沿任务流分别累计学习维护和部署执行两本账，放在同一条曲线上比较；与金额对齐的同一个 agent 比较；以金额报告回本任务数；环境或规则变更后重新测量。
- 我的建议：判断标准见第 8.3 节。这个标准是否合适，任务到达率和变更间隔由谁提供，由 Edwin 决定（第 11 节）。

**对照组。**

Codex 建议（本稿采纳）：主实验四组，当前系统、文字经验、通用修改器、完整方案。这四组只检验完整方案值不值得做。要声称某个方向单独有价值，还要加只做诊断修复、只做环境知识、两者都做（即完整方案）的组件对照，三者共用同一套验收；只做诊断修复的一组仍然允许循环写新 action，只是不提供环境知识。要声称维护有价值，加“知识冻结”对“允许更新”的对照。不通过取消对照组的基本错误检测来制造优势。

我的建议：再加四组简单做法。预算对齐以金额为准：各组学习维护与部署执行两本账的金额之和相同；运行次数、调用数和各组的人工小时另行报告。这类对照在已核对的文献里只有零星的例子，结果不一。

| 对照 | 做法 | 所引工作的条件和结果 |
|---|---|---|
| 多试几次 | 不改 agent，同样的金额用来重试或多选一 | 在一个命令行基准上（两个模型、全部任务），各方法按相同的尝试轮数对齐、没有报告 token 或金额；用单元测试作反馈和最终挑选的依据时，并行采样和顺序修正高于执行框架演化 [E422] [E420] |
| 多给几步 | 不加模块，放宽步数上限，加不调用模型的页面裁剪 | 见问题三第二条 [E428] [E429] [E430] |
| 一次改写 | 同一个模型、同样的起始信息，只改写一次，不跑新的运行 | 在一项技能优化研究里，一次改写低于完整的优化方法，在一个任务上还降低了初始得分 [E620] |
| 随机搜索 | 在同一张改法清单上随机挑，迭代次数相同 | 在一项模块搜索研究里，所提方法高于包括随机搜索在内的各个搜索基线 [E621] |

我的判断：在 [E422] 的设置里，单元测试同时用作重试的反馈和挑选最终结果的依据。部署时没有答案库，所以“多试几次”一组重试和挑选时只能用系统自己的成败检查，检查的时间和费用计入每次尝试；效果仍在最终测试用例上用答案库评分。

实验规模：主实验四组，组件对照两组（第三组就是完整方案），冻结对更新一组，简单做法四组。

**任务顺序和重复。**

Codex 建议（本稿采纳）：连续学习用任务流来测，任务一个接一个到来，处理当前任务时只能用之前任务的反馈；报告不同任务顺序和随机重复下的变化。

文献结论：一项对两种记忆方法的重新评测里（预印本，每个实验三次运行），其中一种在默认顺序下略有提升，打乱顺序后变成下降；作者认为默认顺序隐含着由易到难的安排 [E403] [E402]。这类方法在多数情形下增大了多次运行之间的差异 [E401]。对其中一种方法在一个网页基准上的总体收益，三次运行和追加到六次运行都不能把它与运行间的波动分开 [E622]。另一项流式评测里（预印本），五种自进化方法的平均收益对一个模型为负，对另两个模型为小幅正值 [E464]。

我的建议：任务流的用例不从最终测试用例里取；每个任务按它得到自己的反馈之前的那次结果计分；运行中看到的任务流结果不用来调整阈值、改法或停止时机；每种顺序做多次独立运行，报告结果的分布；写明运行时能拿到的反馈是答案库的对错，还是只有系统自己的信号。

**贡献的说法。** Codex 建议（本稿采纳）：只有在上述对照上得到稳定的证据，才把诊断选择、环境表示或验收机制里有效的部分写成方法贡献；如果组合系统只有工程整合的效果，如实写。要声称优于某项最近的工作，需要可比的复现，或清楚说明适配上的差异。

| 环节 | 在循环内还是循环外 | 与全自动的关系 |
|---|---|---|
| 确认答案库的用例（第 5.1、5.3 节） | 循环外。循环开始之前一次；规则或系统变更后，为新增和改动的用例再做 | 用户要求的一部分。持续运行时，每次规则变更后都需要人参与 |

| 对新通过的改动抽样复核（第 5.4 节） | 循环外，不阻塞循环 | 不冲突；用来量验收的误判率 |
| 抽样核对评分（第 5.6 节） | 循环外，属于研究测评 | 不冲突 |
| 运行时的询问或规划 | 业务执行中 | 用户要求。问的是谁待 Edwin 确认；如果是问用户，它是业务的一部分，不算循环里的人工 |

| 改动用于真实填报之前的审核 | 循环外，上线环节 | 见下表 |

改动上线前人管到哪一步，三个选项：

| 选项 | 做法 | 与用户要求的关系 |
|---|---|---|
| 逐次审核 | 每次保留改动都由人审核 | 循环不能无人连续跑，不符合全自动，不采用 |
| 上线前审核 | 循环自动保留或回滚；改动用于真实填报之前，由人审核一次 | 循环本身不用人，已经满足全自动 |
| 上线也自动 | 上线前的审核也去掉 | 超出了用户说过的范围 |

我的建议：用“上线前审核”。理由有三条。在一项技能演化评测中（预印本，只在一个交易环境里做 [E623]，所引条目没有说明模型和样本量），带改进和回归条件的验收仍会放进有害的改动，也会漏掉好的改动，选择时的验证与留出评测的一致率只有一半多 [E624]。在代码修复的研究里，通过了测试的补丁有一部分在独立复查中不成立 [E543] [E547]。上线后的 agent 会真实提交填报。

是否以“上线也自动”为目标，由 Edwin 决定。如果要走向它，转换条件事先定好，例如另建一份审核用例（不属于开发、筛选、最终测试三份中的任何一份，不参与保留或回滚，费用记在研究测评账本），在上面量出“通过验收但其实错了”的比例低于某个值。

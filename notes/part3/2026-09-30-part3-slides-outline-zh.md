## 第 1 页　我们要做的事

**一句话：** 对固定的一类重复任务、固定的模型，在做对的前提下，让 agent 从自己做过的运行里学，把下一次做得更快、更省钱。

页面内容：
- 三个限定各一行：任务是重复的（同一张表、换一个人）；模型不能训练（只能改模型外面的东西：提示词、记忆、动作、代码）；"更快更省"必须在做对的前提下比。
- 一行背景：我们查过的 432 篇文献里没有统一的"agent 加速"定义，把速度或费用写进所要解决的问题的只有 151 篇。

参考：本次定位研究的计数（我们自己的统计）；Cost-of-Pass（ICLR 2026）——"做对一次要花多少"这个比较口径的出处，第一部分已引用。

## 第 2 页　现在为什么慢又贵：每次都从头摸索

**一句话：** agent 不记得上次怎么做的，同样的事每次重新摸索一遍。

页面内容：
- 一个例子：人 30 秒做完的手机任务，agent 要两分多钟、每次一美元以上（MobileGPT 的作者自己的描述）。
- 三句归因（都是论文原话的意思）：每次交互都要打开页面、点、猜、重试，而且每个 agent 各付一遍；会话结束就把轨迹和反思丢掉；存下来的经验是一段文字，下次还得让模型重新读、重新规划。
- 一张小图：第 1 次和第 N 次运行的时间、费用几乎一样高（示意，不是数据）。

参考：MobileGPT（MobiCom 2024）；"Internal APIs Are All You Need"（预印本，机构合格）；Metis（预印本）；TraceCompiler（预印本）；EchoPath（预印本）。

## 第 3 页　方向一：把"看轨迹→找问题→改→重测"变成自动循环

**一句话：** 现在这个循环是人带着编程 agent 手工做的，我们要让它自己转。

页面内容：
- 循环的七个环节（方案稿 4.1）：收集运行 → 找问题（失败，以及做对了但很浪费的运行）→ 归因 → 分类 → 选改法（改提示词 / 写新动作 / 改代码 / 留给模型每次判断）→ 改 → 验收。
- 两道验收（方案稿 4.5）：先逐个用例看正确性不能变差；再看每做对一次的时间和费用有没有变好。
- 文献里的自动版本做到哪：改自己代码的（DGM：SWE-bench 子集 20%→50%，单次运行；SICA：17%→53%）；改提示词的（GEPA：比强化学习少用最多 35 倍的试运行）；先找"该改哪一块"再改的（JudgeFlow）。
- 一行提醒：这些工作挑版本时几乎只看分数；把时间和费用写进挑选标准的只有 SICA 一篇。

参考：DGM（ICLR 2026）；HGM（ICLR 2026 oral）；SICA（ICLR 2025 workshop，按机构计）；GEPA（ICLR 2026 oral）；JudgeFlow（预印本）。

## 第 4 页　方向二：从做过的运行里学会环境，变成下次能直接用的东西

**一句话：** 哪个按钮通到哪一页、字段接受什么、哪些步骤是固定的——学一次，下次不再问模型。

页面内容：
- 三个已有的做法和数字：同一任务换参数再做，时间省 62.5%、费用省 68.8%（MobileGPT，条件：记忆经人修过，第一次反而更贵）；先离线把网站摸清，运行时模型只调用一次，每题 87 秒→27 秒、0.40 美元→0.05 美元（ActionEngine，条件：评测前用每类任务的一个实例预热过）；经验先存成文字，被反复用到才变成代码（Metis，执行 token 省 13.5%–22.8%）。
- 一行边界：这些都是在网页和手机应用上做的；企业业务软件的表单流程上，我们核对过的文献里没有找到。

参考：MobileGPT；ActionEngine（预印本）；Metis（预印本）；WALT（ICLR 2026）；Agent JIT（ICML 2026）；SpeedRunner（预印本）。

## 第 5 页　哪些经验能变成代码，哪些只能留给模型判断

**一句话：** 不是所有经验都能写成代码——能确定的写成代码，要判断的留给模型，形态是由经验的性质决定的，不是我们随便选的。

页面内容：
- 一张两栏表：
  - 能写成代码的：字段之间的依赖、算术、格式校验、审批的前置条件、固定的点击顺序。
  - 只能留成文字提示、每次由模型判断的：这张票据属于哪一类、这笔费用合不合理、信息不全时该不该问人。
  - 不写成代码的：提交这类无法撤回的操作，在轨迹还不能完全确定后果时。
- 文献支持：Growing Harness 的规则是"确定的、可复用的操作写成代码，模型调用留给需要语义判断的地方"；Metis 的规则是"被反复选中够次数才编译"；SKILL.nb 用执行证据逐步决定哪些步骤固化、哪些保留给模型。
- 为什么要分：留成文字的经验每次都要读进上下文，步数略降但 token 常常上升（WebCoach、Meta-TTL、CTIM-Rover）；变成代码的才同时省步数和 token。但文字不一定更差：Metis 自己的消融里，只用文字记忆也省了 token。

参考：Growing Harness（预印本）；Metis；SKILL.nb（ICML 2026 workshop）；TraceCompiler；WebCoach（ICLR 2026 workshop）、Meta-TTL（ICML 2026 workshop）；CTIM-Rover（REALM 2025 workshop，按机构计）。

## 第 6 页　怎么判断 agent 做对了没有

**一句话：** 判断对错是整件事里最不可靠的一环，所以我们用书面规则事先造好"标准答案库"，它只负责判对错。

页面内容：
- 文献里判断对错的四种办法：
  1. 标准答案（ground truth）：评测集的作者事先准备好正确结果——标准答案、单元测试、或"任务完成后系统状态应该是什么"的检查程序。多数论文用这个，由人写或由程序按已知规则生成。
  2. 让另一个模型当裁判：便宜，但与标准答案的一致率只有 72.7%（ReasoningBank）；Agent-as-a-Judge 做到约 90%，普通模型裁判约 70%。
  3. 不需要答案的程序检查：工具调用有没有报错、代码能不能编译。漏洞明显——"不报错就算通过"放过过坏函数（SkillWeaver）。
  4. agent 自己写测试：对标准答案的精确率只有 56.9%（OpenSkill）；另一篇去掉自写测试后通过率从 71.1% 掉到 41.1%，但作者说标准答案仍然不可缺（CoEvoSkills）。
- 我们的做法（用户要求）：模型从规则手册推出各种情形（含边角情形），生成用例和应该怎么填，人简单确认。答案库只用来判对错，不参与改进；循环不能改答案库、评分程序和规则文本。
- 借用的一条：按"任务结束后的系统状态"判分，既查该变的变了，也查不该变的没变（AppWorld）。

参考：ReasoningBank（ICLR 2026）；Agent-as-a-Judge（ICML 2025）；OpenSkill（EMNLP 2026）；CoEvoSkills（COLM 2026）；SkillWeaver（预印本）；AppWorld（ACL 2024）。

## 第 7 页　改进本身也要花钱

**一句话：** 让 agent 变好的过程自己要花时间和钱，而且主要花在"验证每个改动到底好不好"上。

页面内容：
- 文献数字：一项工作里验证评估占搜索所用 token 的 65–69%（RQGM）；一套提示词优化实验合计 86 美元（GEPA，六个基准）；各项工作报告的改进开销从几美元到两万美元不等（自改进文档 7.2 节的表）。
- 学到的东西还可能让以后每次运行更贵：提示词越改越长、记忆越存越多（ESPO、"Are Online Skill and Memory Modules Worth Their Tokens"）。
- 所以我们分三本账记（方案稿 8.3）：日常运行花的、学习和维护花的、做研究测评花的；每一笔只进一本。
- 省验证开销的办法（文献里现成的五种）：验证用例少而准；便宜的检查挡在前面；一个用例不行就早停；先小规模再扩大；搜索阶段用便宜模型。

参考：RQGM（预印本）；GEPA；DGM；ESPO（EMNLP 2026 Findings）；"Worth Their Tokens"（EMNLP 2026）；SEDM（NeurIPS 2025 workshop）。

## 第 8 页　实验里跟谁比

**一句话：** 文献里有三个"看起来有效、换个比法就没了"的例子，它们告诉我们对照组必须怎么设。

页面内容（每条：反例 → 我们因此怎么设对照）：
1. **给普通 agent 同样多的预算，它就追平了。** 一项研究把在线记忆、工作流、技能三种模块和"不加模块、只是多给几步"的普通 agent 比，给同样多的 token，普通 agent 持平或更好。→ 我们的对照组不能是"什么都不做的原系统"，而是"拿到同样多的钱、可以多试几次或多走几步的原系统"。
2. **换到没见过的真实任务上，收益消失。** 把跨任务记忆搬到真实的软件工程任务上，成功率 40% 对不加记忆的 42%，只用记忆时掉到 31%（CTIM-Rover）。→ 我们报告结果用的用例，必须是改进过程从没用过的；同一模板换参数和真正的新情形分开报。
3. **多加一个环节不一定有用。** 一个受控实验发现"按失败原因分配改进预算"和平均分配没有可检出的差别。→ 我们每加一个环节（分类、环境知识、按成本排序），都要有一组把它关掉的对照，并且重复多次运行。

对照组清单（方案稿第 9 节）：主实验四组——当前系统、只加文字经验、通用修改器、完整方案；四个简单做法——多试几次、多给几步、只改写一次、随机挑改法；各组花的钱对齐。

参考："Are Online Skill and Memory Modules Worth Their Tokens"（EMNLP 2026）；CTIM-Rover（REALM 2025 workshop，按机构计）；"Coverage, Not Credit"（预印本）。

## 第 9 页　实验怎么做

**一句话：** 一个重复的填报流程，四个阶段，每一步都能给出"不值得做"的结论。

页面内容：
- **任务和答案库：** 选定一个填报流程和它的运行环境（待 Edwin 定）；从规则手册生成用例和正确填法，人确认；答案库分三份——开发用例（循环可以看失败原因）、筛选用例（决定留哪个版本）、最终测试用例（方案定了以后才用一次）。
- **怎么评分：** 程序核对最终结果——先看处理方式对不对（提交、拒绝、询问），再逐字段比；每个用例重复跑，同时报"每次都对"的比例；抽样人工复核评分。
- **量什么：** 做对的比例；每做对一次的时间和钱；三本账各花多少；学习花的钱跑多少个任务能赚回来。调用次数、步数、token 只用来解释原因，不作为保留改动的条件。
- **四个阶段（方案稿第 10 节）：**
  1. 搭台：轨迹记录、答案库第一版、评分程序、量现有系统的时间和费用构成。任务不能重复跑或结果无法独立判断就停。
  2. 两个方向分别做最小验证：轨迹诊断到候选改动的循环；同一批轨迹上比较"文字经验 / 直接变成技能 / 带出处和条件的环境知识"。改动大多通不过验收就停；简单做法够用就保留简单做法。
  3. 完整方案加消融；任务一个接一个到来的连续学习；规则或界面变了之后的维护。估算的回本任务数超过一次变更间隔内的任务量就停。
  4. 可选：训练一个小的编辑模型，或换一个填报任务。
- **人在哪里参与：** 确认答案库、给检测器做少量标注、抽样复核——都在循环之外；改动用于真实填报之前由人审一次（建议）。

参考：方案稿第 5、9、10 节；LATM（ICLR 2024）与"Inefficiencies of Meta Agents for Agent Design"（EMNLP 2025 Findings）——回本的算法出处。

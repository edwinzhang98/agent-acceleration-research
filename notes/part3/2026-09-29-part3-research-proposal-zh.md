# 从执行轨迹学习的 Agent 加速研究方案

第三部分研究方向与已有工作的关系

2026年9月29日　版本 0.1

> 状态更新：本稿是尚未确认的早期方案。用户随后要求先系统调查相关工作；新增调查发现更直接的自动改进、环境学习和 RL 先例。请先阅读 [相关工作调查](../research/2026-09-29-part3-related-work-survey.md)，再讨论方法与实验；同名 Word 版保留为原始草稿。

我们准备研究一种从执行经验中持续改进的 Agent 系统。在反复使用同一类软件环境时，系统收集成功和失败的执行轨迹，识别反复出现的错误与高成本操作，提出对代码、提示词或动作能力的修改，并通过后续实验判断这些修改是否让任务完成得更快、更便宜，同时保持任务质量。

研究包含两个相互支持的方向。第一个方向是自动运行目前由人推动的诊断和改进过程，回答“Agent 的什么地方需要改，怎样改，怎样证明改好了”。第二个方向是从轨迹中积累对环境交互的认识，回答“哪些操作规律已经足够可靠，可以变成可复用的动作；哪些部分仍需根据当前状态判断”。Concur 报销流程可以作为首个验证场景，之后再检验方法能否迁移到其他工作流。

已有研究已经覆盖了这两个方向的若干核心机制，有的工作与整个闭环也非常接近。本稿提出一个可讨论的切入点：在给定学习投入和任务质量要求下，依据真实错误与时间、费用记录来选择改进对象，并显式记录动作的适用条件，能否比已有自动优化和技能学习方法获得更多可持续的执行收益。原始目标仍是自动改进与环境学习；这里的排序方式、环境表示和修改范围都是候选设计，尚待讨论和实验检验。

## 一 与前两部分的衔接

第一部分已经建立了统一的衡量方式：任务耗时来自执行步数、每步模型调用、单次调用耗时、模型之外的耗时及它们之间的重叠；费用来自不同类别的 token 与环境使用，最终还要考虑成功率。第二部分按这些项介绍已有加速方法，也指出每种方法可能增加的其他开销。第三部分沿用这一目标和衡量方式，把研究对象推进到“如何根据执行经验选择并持续更新这些改进”。

因此，第三部分可以这样承接：我们已经知道有哪些加速手段，现在希望研究一个能从自身轨迹中判断何时使用哪些手段、生成必要修改并验证收益的过程。首轮范围集中在执行逻辑、提示词和动作能力；服务端调度、硬件和模型供应商的价格档位作为实验条件固定。

| 前两部分的内容 | 本研究怎样接上 | 必须保留的测量边界 |
| --- | --- | --- |
| Part 1 第03至04b页的时间与费用定义 | 给每条轨迹和候选修改记录实际耗时、调用、token、费用与成功情况 | 缩短输出不等于缩短总耗时；减少调用也不保证总费用下降 |
| Part 2 第03页的编译与重放 | 把已确认的操作规律转成可执行代码，减少例行操作中的模型调用 J_i | 底层点击和页面等待可能仍然存在 |
| Part 2 第04页的较大动作与技能 | 从多条轨迹中生成、修复和组合动作，减少反复规划和绕路 | 高层步数 N 下降时，也要记录展开后的底层动作数 |
| Part 2 第06和11页的观察与上下文管理 | 必要时修改信息获取或提示词，避免反复读取无关内容 | 环境知识和技能说明本身也会增加输入长度 |
| Part 2 第08页与附录B8的环境开销及成功成本 | 追踪执行开销、失败恢复和学习投入是否被后续任务抵回 | 所有失败尝试、分析、生成与验证开销都应保留 |

这些对应关系解释了本项目为什么属于 Agent 加速研究。我们主要希望减少重复决策、重复探索和错误恢复；这些改进可能同时影响 N、J_i、上下文长度和成功率。具体改变了哪一项，需要从执行记录中验证。

## 二 两个方向共享的学习过程

系统可以分成执行任务和改进系统两个过程。执行过程使用当前版本的 Agent、环境知识和动作库完成任务。改进过程在一批任务之后读取轨迹，提出候选修改，经过验证再形成下一版本。每条轨迹都需要记录由哪个版本产生，避免把不同版本的效果混在一起。

一条可分析的轨迹应包含任务目标、可见状态、动作及参数、环境返回、实际完成结果，以及模型与工具调用的时间和费用。动作库内部展开的步骤也需要保留，否则一个表面上成功返回的动作可能掩盖内部重试或静默失败。历史问题、尝试过的修复及其结果应能被下一轮分析继续使用。

我们设想的闭环为：执行任务并留下记录，聚合反复出现的问题，提出原因假设和对应修改，实施候选方案，在开发与回归任务上比较，保留有效版本，再在新的任务中继续收集证据。轨迹解释只是原因假设；修改之后的对照结果，才是判断这个原因是否有用的关键证据。

下面用一个假设例子说明两个方向如何配合。Agent 在选择费用类型时，多次打开同一个菜单、搜索选项、点错后返回，最终完成了填写。分析器发现这段操作出现频繁、耗时较高；它需要进一步区分：错误来自选项定位、费用分类判断，还是菜单存在尚未观察到的条件。环境学习可以形成“菜单怎样打开、选项怎样定位、选择后怎样确认”的可复用操作。费用应该归到哪一类，则可能仍需读取当前单据并判断。这样，稳定的界面操作与当次任务的语义判断各自有明确职责。

这个例子只说明拟研究的行为，不是已有 Concur 测量，也不预设全部轨迹问题都能编译成固定代码。

## 三 方向一 自动诊断并改进 Agent

方向一要自动化的是当前人工工作的主要环节：找出值得处理的问题，形成可检验的原因解释，选择修改位置，生成修改，并检查收益和回归。输入需要同时包含失败轨迹与成功但低效的轨迹。只看失败会漏掉可压缩的重复操作；只看成功又可能复制偶然奏效的路径。

问题的优先级应结合出现频率、单次损失、影响的任务范围，以及预计修复和验证的成本。高频的小问题与低频但代价很高的问题都可能值得处理。初始系统可以采用可解释的排序规则，之后再研究排序策略是否需要学习。当前不预设一个已经验证有效的优先级公式。

| 观察到的现象 | 待验证的原因假设 | 候选修改 |
| --- | --- | --- |
| 同一 action 经常找不到目标或执行到一半中断 | 定位、参数、状态检查或代码逻辑不完整 | 修复 action 的实现与结果检查 |
| 相同的操作序列反复由模型逐步推导 | 缺少可复用的动作抽象 | 创建或组合参数化动作 |
| 动作正确但任务要求经常理解错误 | 提示词、规则检索或信息输入不足 | 修改提示词或信息获取方式 |
| 先前有效的操作在某些状态下失效 | 适用条件遗漏或环境已经变化 | 缩小动作适用范围，更新环境记录 |
| 下一步依赖当前才出现的信息 | 必须在线获取信息并作决策 | 保留观察或规划节点，改进触发时机 |

候选修改需要有明确的预期：它针对哪一类问题，预计减少哪些调用或等待，可能影响哪些任务。首轮可以约束每次修改的范围，使收益和退化更容易归因。评估器、评分规则和最终测试任务保持独立，避免修改系统通过改变评价方式获得表面提升。

在这一方向中，值得验证的机制包括：保留跨轮问题记录是否有帮助；依据时间与费用而非仅成功率来排序问题是否有帮助；明确选择修改位置是否优于把全部轨迹交给一个通用 coding agent 自由修改。这些问题都需要强对照，不能仅凭流程完整就认定有研究贡献。

## 四 方向二 学习环境并形成可靠动作

方向二希望把跨任务稳定的交互规律保留下来。这里的环境知识可以从局部开始：某类页面暴露哪些操作，什么条件下可以执行，参数从哪里取得，执行后应发生什么可观察变化，以及已经遇到哪些例外。它不需要一开始就覆盖整个网站，也不能由有限轨迹推出完整环境已经被恢复。

同一个界面外观可能对应不同的权限、数据或后端状态。因此，环境记录应保留条件和反例。例如“点击后通常出现这个对话框”只有在页面状态、账号权限等条件成立时才可使用。知识库保存读取数据的方法和结构，当前选项、权限及业务数据仍在执行时获取。不能确认适用条件时，应继续观察或交由模型判断，并把新的结果加入后续学习。

一个候选动作可以包含名称、参数、前置条件、执行逻辑、结果检查，以及适用证据和失败时的恢复方式。动作创建后，要在不同任务参数和起始状态下验证。收益来自它在一类任务中可靠复用，而不只是重现某一条成功轨迹。

环境知识还可以帮助方向一缩小诊断范围。当代码按照已知交互规则执行却得到意外结果时，系统可以检查规则是否过期；当环境状态符合预期但选择了错误操作时，则应检查规划或提示词。明确记录这些区别，有机会减少对同一问题的反复误修。

本方向拟优先研究“从已有任务轨迹出发，按问题需要补充探索”的方式。它与预先全面爬取环境的投入方式不同，但是否更省成本、更容易覆盖重要交互，需要和已有方法比较。探索也可能引入额外费用，甚至遗漏低频关键状态；这些都应反映在最终效果里。

## 五 已有工作已经做到什么

下面的工作提供了最直接的起点与对照。它们的存在支持这些技术路线具有可实现性，同时也收窄了我们能够主张的创新范围。这里按与本项目的关系使用证据，不把不同基准上的效果数字直接搬作本项目的预期收益。

**GEPA 已经展示了从轨迹反思到提示词更新的自动搜索。** 它读取推理、工具调用和反馈，提出并评估候选提示词，积累有效修改。[1] 因此，自动发现错误后修改 prompt 应作为已有能力和对照方法。其作者维护的工具也扩展到了代码等优化对象，不能把整个框架简单限定为“只能改 prompt”。

**ADIAS 与方向一的完整过程尤其接近。** 它跨轮保留问题身份、状态、支持证据和干预历史，据此选择修复目标并修改 Agent 代码。[2] 其交互基准中的效率量是任务得分与平均环境步数之比，不能直接解释为实测时间或美元收益。这意味着“自动归因再改代码”以及“跨轮记住失败问题”本身都不足以构成我们的新颖性。我们需要比较，在相同投入下，增加对耗时与费用的定位、结合环境交互知识，究竟改变了哪些决策和结果。

**SpeedRunner 是连接两条方向的直接近邻。** 它让 coding agent 分析历史轨迹，诊断失败和回归，修改可执行技能库，并研究成本随学习过程的变化。[3] 它在在线设定中不要求反复重放同一任务来验证每个修改；论文的阶段性测试也不能等同于逐补丁的部署验证。它应成为本项目必须认真比较的方法，不能将“trajectory 变成代码技能从而省钱”当成空白。

**SkillWeaver 已经把网站探索转化为经过练习和改进的 API。** 它自主发现技能、执行练习，并把经验整理为可调用的程序能力。[4] 其主要证据是成功率；附录还记录了技能通过吞掉异常而被错误判为有效的失败案例。这提醒我们，验证必须检查任务实际结果，不能把“没有报错”视为动作正确。“自主探索后生成新 action”已经有明确先例。

**ActionEngine 已经显式学习环境交互结构。** 最新 v2 将界面状态、可用操作与状态转移组织为可更新的状态机记忆，再生成程序完成任务；架构包含失败修复和记忆更新。[5] 但正式评测前使用任务模板生成任务做热身，评测中关闭了修复模块，因此结果不等同于未见模板泛化或持续在线自我修复。它也报告了爬取成本与摊销；该口径不能自动当作包含热身、维护在内的全部学习成本。本项目需要直接比较按真实问题补充知识的方式，是否在覆盖、适用判断或投入上有增量价值。

**WALT 已经研究自主探索并创建可复用的 Web 工具。** 它探索网站功能、生成交互示范，再构建和验证工具，涵盖参数化、前置条件、执行反馈和工具改进。[6] 给动作增加条件和结果检查有明确工程价值，但这些构件本身也需要放在已有工作中定位。

由这些证据出发，当前更合适的研究问题是：在反复执行的 Web 工作流中，以质量要求为约束，结合跨轨迹的问题分析与局部环境知识，是否能更有效地分配学习和验证投入，从而改善后续任务的时间与费用。仅把几个已有模块连接起来还不能证明贡献；必须显示具体设计相对于直接组合或复现已有方法的增量作用。

## 六 首轮可以验证的最小方案

首轮建议固定基础模型和浏览器工具接口，在一个能够获得可信任务结果、能够运行开发与回归实验的环境中，选择若干有重复结构的任务族。先检查现有轨迹是否包含足够的状态、时间、费用与结果记录，再决定补采什么数据。Concur 是候选起点；如果真实环境无法可靠重置，应以可重置环境完成因果对照，并另行评估真实环境的连续使用效果。

初始实现保留一个执行 Agent、轨迹存储、候选修改生成器和独立评估器。方向一先支持少量明确的修改出口，例如提示词、动作实现与新动作。方向二先维护与当前任务族有关的局部交互记录，不追求完整网站模型。先验证闭环是否能自动产生可复用的有效修改，再讨论更复杂的学习算法。

建议把三个问题作为首轮要回答的研究假设。其一，时间和费用记录能否帮助系统优先修复对效率影响更大的问题。其二，显式记录环境条件和执行结果，能否减少动作误用和重复探索。其三，两者结合后的收益，能否抵回分析、探索、生成和验证的额外投入。任何一项都可能得到否定结果；这种结果可以帮助我们收缩或调整方案。

强化学习保留为后续候选。如果需要学习“下一轮探索哪里”“哪个修改最值得试”或“何时使用动作、何时继续规划”的策略，可以进一步定义状态、可选决策和奖励。首轮不把训练基础模型权重设为前提。先用自动搜索和实测反馈建立可运行对照，能够更清楚地判断 RL 是否带来额外价值。

## 七 怎样证明系统确实在加速

外部对照的候选集合包括不跨任务学习的原始 Agent、直接检索历史经验、提示词优化、SpeedRunner 式技能学习，以及 ActionEngine 式环境记忆。方向一涉及自动修改完整执行逻辑时，ADIAS 式自动优化是重要对照。首轮根据最终主张和可复现性选择最直接的强对照，其余逐步扩展。实现有适配时，需要说明改了哪些接口或能力；不能将一个明显弱化的复现当成原方法。

内部可以采用一个四组设计，分别打开和关闭两项能力。为使比较可解释，“方向一”在这里指带跨轨迹归因和效率排序的改进控制器；“方向二”指显式环境交互记录及其动作适用判断。所有组都保留相同的基本候选生成和评估设施，否则无法区分收益来自哪个机制。

| 组别 | 改进目标怎样选择 | 环境知识怎样提供 |
| --- | --- | --- |
| 基础组 | 通用反馈驱动修改 | 只使用任务轨迹与普通技能说明 |
| 仅加强诊断 | 跨轨迹问题记录与效率排序 | 与基础组一致 |
| 仅加强环境知识 | 与基础组一致 | 提供显式交互条件与结果记录 |
| 联合方案 | 跨轨迹问题记录与效率排序 | 提供显式交互条件与结果记录 |

四组设计首先用于筛选两组能力的组合价值，不能代替与已有强方法的比较。若要进一步主张效率排序有效，需要保留相同的问题记录和诊断，只移除时间与费用排序，再做单独对照。各组使用相同的初始信息、任务来源、工具权限和资源约束，自行收集的额外轨迹和知识均计入投入；优先比较同等累计学习费用下的效果，并辅以调用和环境交互统计。对质量未达到预定要求的修改，不能因为执行更快就判为改进。

评价同时报告任务成功率、完整任务耗时和费用，以及调用次数、底层动作数、重试、上下文和动作复用情况。高层动作把多个步骤包装起来时，步数下降本身不足以证明加速。耗时由任务开始到实际完成的时间戳测量；失败和超时应保留，避免只统计成功样本而产生偏差。

自动化程度也需要单独验证。记录每一轮是否需要人提供原因、指定修改方向、处理运行故障或决定候选去留，以及能够连续自主完成多少轮。人工定义任务和验收标准属于初始设置；逐轮提示或接续属于运行中的干预，应报告次数和原因。这样才能判断是否真正减少了人推动闭环的工作。

学习过程需要另外报告冷启动投入、随任务推进的效果，以及包括探索、分析、候选生成、验证、被丢弃方案和执行在内的累计费用。离线学习耗时与用户等待时间分别记录；如果学习阻塞下一任务，其阻塞也计入任务体验。成功成本使用同一观察期内的全部相关费用除以成功完成数，且同时报告成功率与任务数量；成功数为零时不报有限比率。持续更新中的系统版本不断变化，不能把整个学习期解释为同一固定 Agent 的独立重复尝试。

泛化评估分两种协议。第一种在开发结束后冻结版本，测试未参与学习的新任务参数、新流程组合和环境变化；最终测试结果不再反馈到优化器。第二种按任务流持续学习，先记录当前任务结果，再允许其轨迹影响后续任务。这种连续学习测试需要固定任务顺序或多次随机化，并清楚区分“学习前”和“学习后”的成绩。

还需要检查至少三类退化：修好一类问题却破坏旧任务；新动作只对已有实例有效；环境记忆过期后仍被继续使用。数据按工作流模板划分，版本和知识库按实验组独立初始化，避免近似任务或其他组的经验泄漏。

## 八 第三部分可以怎样讲

第三部分的主线可以控制为六页，每页回答一个问题。正文先讲我们准备做什么，再用最近邻工作说明为什么这样设计，最后给出如何证伪的实验。

1. **我们希望执行经验能够持续减少下一次任务的开销。** 承接前两部分的时间、费用和成功率目标，说明目前人工读轨迹、指导修改的实践起点；将其有效性表述为待系统验证的观察。
2. **方向一让系统自动发现问题并验证修改。** 展示执行、分析、修改、验证、继续执行的闭环，以及 code、prompt、action 和动态规划几个出口。
3. **方向二让系统积累对环境交互的认识。** 用一个假设的费用类型选择例子，展示局部环境知识怎样变成带适用条件和结果检查的动作。
4. **已有工作给出了基础能力和强对照。** 选择 ADIAS、SpeedRunner、ActionEngine 三个最邻近例子，把已经覆盖的内容说清楚；GEPA、SkillWeaver、WALT 作为补充来源。
5. **我们首先验证效率驱动的修改选择和环境知识是否有增量价值。** 把候选方案和三个研究假设放在一起，明确模型、场景、修改范围以及尚未决定的部分。
6. **我们用质量约束下的执行收益和全周期投入检验方案。** 展示对照、消融与累计学习曲线需要回答的问题，为后续预算阶段列出实验规模变量。

其中最值得展开的是一个贯穿例子：轨迹暴露了什么问题，系统怎样区分原因，形成什么修改，后续任务怎样复用，以及怎样发现修改无效。它能让读者理解研究对象，也能避免整段内容停留在抽象流程图。

## 九 下一轮讨论需要确定的内容

首先需要确认首个环境和任务族，以及可获得的轨迹、任务结果和重置能力。这决定了我们能否开展可信的回归比较，也决定了应该采用离线验证还是连续任务流协议。

其次需要确定第一项主张的重心。可以优先研究方向一的改进选择机制，也可以优先研究方向二的环境知识与动作适用性，再把另一方向作为支撑。如果首轮同时研究全部修改出口、完整环境建模与 RL，结果很难归因，实验投入也难控制。

还需确定任务质量的接受标准、允许自动修改的范围，以及与哪些最近邻方法做可执行对照。确认这些之后，再确定任务量、重复次数、学习轮数、每轮候选数和探索限额，用小规模试验测得真实调用与耗时分布，进入预算计算。

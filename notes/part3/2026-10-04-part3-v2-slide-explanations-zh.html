封面 研究的核心问题

打开这一页

  • 我们关心的是：一个 agent 反复在同一个网站做类似任务，能不能从之前的经历里学到东西，让后面的任务更快、更便宜？
  • “环境稳定”是指网站和主要工作流程相对固定。每次的输入可以不同，例如换一个人、换一趟出差、换一批收据。
  • ExpenseAI 是我们的具体场景：在同一个 Concur 系统里填写不同的报销单。
  • 我们会先看它为什么重复花时间，再解释测试数据怎么生成、结果怎么评分，最后回到真实轨迹里的加速机会。

第 1 页 ExpenseAI 在做什么 为什么会反复尝试

打开这一页

这一页先让大家看到一个完整任务，再看到时间是怎么浪费掉的。

  • 一趟 trip 对应一份报销单。Agent 打开报销单，添加费用、选择类型、填写字段、上传收据、保存；酒店费用还要逐晚拆分，最后检查列表里有没有这条费用。
  • 这里的 Save 是保存费用条目。Agent 不会把整份报销单正式提交给审批人。
  • 正常情况下，走完一遍就能完成一条费用。但实际会出现两种返工循环。

第一种是规则问题：做了，但是不符合要求。

  • 例如 Business Purpose 里写了 O'Hare，网站不接受其中的撇号。
  • Agent 要退回去改字段，再保存。后来我们把这条网站规则写进 prompt，记录中的后续运行没有再出现这个问题。
  • 这类经验可以保存成提示、记忆或者网站知识。报销政策本身“该不该报、怎么报”的判断，也属于需要掌握的知识。

第二种是界面问题：操作失败，或者成功了却被误判为失败。

  • 例如控件没有及时出现、对错误类型的控件执行输入、弹窗挡住操作，或者保存以后页面反馈不可靠。
  • Trip R 就是保存已经成功，但弹窗说 Not Found，agent 因而反复保存。
  • 图里在多个环节各标一次 interface loop，意思是这些环节都观察到过这种问题，不是说每一轮都会失败。

右边三组柱子要分开读，因为单位不同。

  • 第一组是出现 Concur 错误的运行数：费用条目错误 36、参会人错误 14、非法字符 3。同一次运行可能落进不止一类，不能直接相加当作独立运行总数。
  • 第二组是操作次数：11,103 次操作尝试中，244 次失败，约 2.2%；下面再按错误信息分成超时 166、不兼容操作 42、页面或元素过期 17、弹窗阻挡 12、其他 7。
  • 第三组是基础设施问题：64 次整趟任务运行里，7 次崩溃或无法开始。这又是另一个统计口径。
  • 底下三句话对应处理办法：规则问题记下来；界面问题改工具或执行框架；服务故障另行修复和重跑，但发生的时间与费用仍然要记账。

第 2 页 为什么加速并不是简单少走几步

打开这一页

这五个困难分成两组：学完以后运行有多贵，以及为了学会它先花了多少。

  • 1. 步数少了，不代表时间少了。 图里的 WebCoach 例子从 10.7 步降到 10.2 步，但时间从 215 秒涨到 395 秒。每一步多读、多想，也可能把省掉的步骤抵消。所以要同时看秒数、费用和结果质量。
  • 2. 哪些观察可以安全跳过？ 例如选完 Hotel，过去都能直接填写日期，是否还要再读一次页面？如果页面状态和规则没变，可以省一步；如果变了，直接照旧操作就可能失败并返工。问题是如何判断“这次仍然可以沿用经验”。
  • 3. 泛化能力和每次使用成本之间有取舍。 固定脚本便宜，但换页面可能失效；自然语言经验灵活，但每次都需要模型读懂并执行。图里的位置是示意关系，不是这些方法的实测排名。
  • 4. 报错不等于告诉了我们原因。 一个“超过餐费限制”的错误，可能来自费用类型选错、规则变化、填错字段，或者金额被工具读错。要找到能修复的原因，还需要额外检查。
  • 5. 学习和验证可能比节省的钱还贵。 找问题、生成修改、跑测试都要付费。只有后续足够多的任务复用这次改进，才可能把前面的投入赚回来；网站变化又可能要求重新学习。

这一页想引出的研究要求： 保持任务质量，同时计算运行成本和学习成本，不能只拿“少了几步”证明已经加速。

第 3 页 数据是怎么一步步生成的

打开这一页

可以把整条链讲成：规则 → 测试情境 → 具体文件 → 一整趟任务 → 运行与评分。

  • Policy：原始依据。 从 GW 的报销手册，以及补充的学校网页和联邦规则出发。
  • Provision：一条规则。 共记录 160 条。例如，酒店账单中的个人消费不能报销；住宿费用要逐晚列明。
  • Situation：一种需要判断的情况。 共 267 种。例如，一张酒店账单上同时有房费、税、电影和迷你吧费用，正确做法是只报房费与税。
  • Instance：把情境变成一个具体样本。 为它生成真实外观的文件和对应答案。例如换成芝加哥某酒店，给出明确日期和金额。267 种情境各生成 3 份，共 801 个实例。
  • Trip：把相关样本组织成一份完整报销任务。 共 23 份任务，里面有旅客背景、收据和说明；agent 要把它们填进同一份报销单。
  • Runs and scores：实际执行，再检查结果。 保存了什么、漏了什么、用了多少步骤和钱，都可以回头核对。

贯穿后面几页的例子： 酒店账单总额 1,182.59，但正确报销金额是 1,120.60，因为要扣掉个人消费。我们会一直跟着这个例子看定义、生成、组装和评分。

框底下的路径都是相对于 ~/projects/ExpenseAI/。

  • Provisions：benchmark/pool/coverage.py 和 coverage_newcats.py。
  • Situations：gw_policy_data/experiment/INTERPRETATION.md 和 experiment_newcats/INTERPRETATION.md 的 B/C 部分。
  • Instances：上述两个 experiment 目录中的 files/ 与 answers.json。
  • Trips：testing_cases/，例如 testing_cases/trip_a_chicago/。
  • 评分产物：local_data/batches/<batch>/<trip>/；原始轨迹：local_data/runs/<run-id>/。轨迹目录里有 steps.jsonl、页面观察和截图。这两类运行记录是本机数据。

第 4 页 Provision 是怎么从政策里提取出来的

打开这一页

Provision 就是一条可追溯的规则：内容是什么，以及从哪一页、哪个链接来的。

  • 左边是原始政策截图。下面把其中“个人消费不可报销”提取为 APPB-PERSONAL。
  • 提取出来以后分成两条用途：一条用于设计测试情境；另一条用于给 agent 提供它执行时需要遵循的政策说明。
  • 测试这一边，这一条规则关联 14 种 situation。酒店账单里的电影、迷你吧和健身费用只是其中一个例子。
  • Agent 指导这一边，它看到的是一般政策，例如“这些个人消费不要报”，而不是某趟测试的隐藏答案。

右边是在用两个不同角度划分同一批 160 条规则。

  • 按来源：83 条来自 2024 年版手册；77 条来自补充网页等来源。
  • 按填写时能否执行：149 条会影响 agent 如何处理文件；11 条发生在填写之前或之后，无法通过填一张收据直接执行。
  • 例如预支款结算不是拿到一张收据就能完成的操作，所以要单独标出来。
  • “149 条都有测试情境”表示已记录的可执行规则都有对应测试，并不表示所有现实政策、所有可能情境都已经穷尽。

第 5 页 Situation 究竟包含什么

打开这一页

Situation 不是某一张固定收据，而是“文件是什么、处在什么条件下、应该怎么处理”的完整定义。

  • Situation ID / family： 这是哪一种情况，以及属于哪个费用组。例子属于 lodging，也就是住宿。
  • Document： 输入是什么。这里是一张混有电影、迷你吧、健身费的酒店账单。
  • Conditions： 什么情况下适用。这个例子适用于美国城市，旅客身份和资金来源不限。
  • Handling： 应该采取什么处理方式。这里是 file part，只报其中允许的部分。
  • Answer key： 正确结果的具体要求。生成一条住宿费用，按晚拆分，只计房费和税，整张账单原总额不能直接作为报销金额。
  • Basis： 为什么这样判断。这里有手册页码，也参考了我们自己的酒店账单。
  • Form work： 实际填写需要多复杂。酒店逐晚拆分要进入第二个界面，因此属于 complex。

右边的对照说明：同一种文件，换条件就可能变成另一种 situation。

  • 都是带网络费用的酒店账单，部门资金支付时可以直接包含进去。
  • 换成联邦研究经费，当前答案要求填写并标记这笔网络费的经费限制。
  • 所以不能只按“它是一张酒店账单”决定处理方式，还要看资金、旅客和地点等条件。
  • 左下高亮的是生成样本中的个人费用与原总额，目的是让人看清哪些要扣掉；不是说 agent 输入时一定会收到高亮提示。

第 6 页 五种处理方式以及 Test 的含义

打开这一页

这一页回答：面对一份文件，正确结果可能是什么？

  • File，71 种：正常填入。 例如普通经济舱机票，对应一条航空费用。
  • File + flag，97 种：填入，同时留下提醒或待人工判断的问题。 金额和类型填对了，还不够；该说清楚的问题也必须说出来。
  • Separate out，6 种：拆到不同费用条目或科目。 商务午餐里的酒水要单列，例子中餐费 94.07，酒水部分 41.84。
  • File part，15 种：只填允许的部分。 酒店账单填写 1,120.60，而不是 1,182.59。
  • Not filed，78 种：不生成该费用条目，并说明原因。 例如同行配偶的机票不能和旅客自己的机票一起照报。

底下的两个框解释两个容易混淆的词。

  • Flag has a level： 非旅行数据中区分两级。notice 是告知，例如提醒学校优先使用 P-Card；needs review 是确实需要人判断，例如采购方式或报销处理需要确认。并不是每一条 flag 都表示费用已被拒绝。
  • Judgment call： 这里是一个数据分类用语，指不能直接照抄收据的情况。196 = 267 − 71，包含要提醒、要拆分、只报部分和不报这四类。
  • 196 不是唯一参加测试的部分。 71 种普通填写也需要测试。

Test 不是一种 situation，也不是一张文件。

  • 一次 test 是：某一种 situation 在一次有效 trip-run 中被评分。
  • 例如 Trip A 一次运行评了 22 种 situation，就产生 22 个 tests。重复跑同一趟，还会再次产生测试记录。
  • 所以上面 71、97 等是全体数据中的“情境类型数”；下面 243/253、84/134 等是历史运行中的“通过次数 / 测试次数”。它们不能一一对等。
  • 这些通过率目前来自旅行部分。普通填写约 96%，需要 flag 约 63%，说明在这批记录里，漏掉应提醒的问题尤其突出；不能把 63% 当成全部 267 种情境的总体通过率。

第 8 页 除了费用类型 每种情境还记录什么

打开这一页

这一页补充四个维度：适用条件、填写复杂度、刻意设置的矛盾，以及答案依据。

  • Conditions：什么时候适用。 地点、旅客身份、资金来源都可能改变答案。例如普通本地午餐不报，但在全天本地会议里的午餐，可能要填写并加 flag。
  • 地点这一组是美国城市 85、国外 18、本地 50 英里以内 9、不限地点 155；旅客与资金又分别是另两种分类。这三组是不同维度，不要加在一起。
  • Form work：操作有多复杂。 204 种 simple，63 种 complex。酒店逐晚拆分、额外字段或第二个界面属于复杂填写。
  • “填写复杂”与“政策判断复杂”不是同一个意思。直接照政策报一张酒店账单，也可能要做很多表单操作；反过来，一张简单收据可能需要很难的判断。
  • Trap：故意设置的跨文件矛盾。 旅行情境中有 19 种。例子是实际乘坐一家航空公司，却出现另一家航空公司的 Wi-Fi 收据，测试 agent 能否对照材料发现不一致并提醒。
  • Basis：答案凭什么成立。 228 种引用手册或学校规则；104 种涉及我们明确记录的决定；73 种参考查到的来源；64 种参考经验；19 种参考自己的收据。
  • 这些依据可以重叠，同一种 situation 可能同时参考政策、经验和我们记录的决定，所以 五个数字不能相加当作情境总数。

这页的价值： 后面发现错误时，可以分辨是适用条件没看懂、表单没填好、跨文件矛盾没发现，还是答案依据本身需要复核。

第 9 页 一个 Instance 是怎么生成出来的

打开这一页

Situation 定义“考什么”，instance 把它变成一份具体可用的输入和答案。

  • 左边三张酒店账单来自同一种 situation：都含有需要剔除的个人消费。
  • 变化的是城市、酒店、日期、晚数、房价、税和个人费用金额；不变的是测试的规则和正确处理方式。
  • 每种 situation 生成 3 个实例，所以 267 × 3 = 801 个 instances。
  • 一个实例可能由 1—3 个文件组成，所以实际共有 903 个输入文件。801 是样本数量，903 才是文件数量，两者不是一个单位。

右边展示的是 Trip A 那条酒店费用的完整答案记录。加粗的字段名可以逐项这样解释：

  • receipt：对应哪份收据。
  • expense_type：应该用哪个报销类型或科目。
  • vendor：商户名称；date：费用日期；currency：币种。
  • amount：应该报销的金额，这里是 1,120.60。
  • requires：除基本字段外，还必须完成什么。这里要求住宿 itemization。
  • itemization 里的 nights：每晚日期、房价和房税，不能只填一个总额就结束。
  • city：费用发生的城市。
  • expense_type_contains_any：评分时可接受的类型文字匹配条件，例如包含 LODGING 或 HOTEL。
  • date_alternatives：除了主日期，也接受的日期取法。这里还接受入住日期。
  • situation：这条答案对应哪一种测试情境，便于跨行程统计。
  • unreduced_total：扣除个人费用之前的原总额 1,182.59，用来检查 agent 是否错误地整张照报。

下面三个 bullet 讲的是生成一致性措施。

  • 先把金额算到分，再渲染文件，减少文件与答案之间的金额偏差。
  • 固定输入与随机种子，可以复现相同文件。
  • PDF 明确标注为合成测试文件。
  • 这些措施保证生成过程可控，但不能单独证明政策解释一定正确；政策和我们自己的判断仍要回到对应依据检查。

第 10 页 怎样把样本组织成一整趟任务

打开这一页

Trip 是执行单位：把一个人的背景和相关文件放到一起，让 agent 完成一份报销单。

  • 左上是 Trip A 的文件夹。Agent 能看到 26 份业务文件和 trip_notes.txt。
  • expected.json 是隐藏答案，MANIFEST.md 是情境清单；turns.json 是运行控制文件，不直接作为答案材料交给 agent。里面的指令会按轮发送。
  • 中间的 trip notes 确实是输入的一部分。它告诉 agent 出差目的、日期、资金来源、同行或用餐人员，以及为什么改签等收据上看不到的信息。
  • 例如 Purple Pig 午餐的参会人是谁、返程航班为什么改签，要从 notes 里判断。
  • 右上是分轮输入：Trip A 第一轮 6 份文件，第二轮 2 份酒店材料，第三轮 7 份餐饮材料，第四轮 11 份交通等材料。合计 26 份业务文件。
  • 这是 Trip A 的四轮安排，不是所有 trip 都固定四轮；整个数据中的 trip 可以有 2—6 轮。

底下三个框分别讲组装约束、数据规模和特殊报销机制。

  • A trip must be consistent：一趟合成行程要在背景上讲得通。 同一段行程的交通不能互相冲突，同一时间不能莫名其妙住两家酒店；租车加油日期要和还车安排对应；独立情境要避免碰巧生成同商户、同日期，导致无法区分。这是组装数据的约束，不是新增报销政策。
  • 这里的“一致”也不意味着没有测试陷阱。我们明确设计的矛盾会作为 trap 保留；要避免的是无意生成的矛盾干扰测试。
  • 23 trips： A—O 是 15 份旅行任务，覆盖全部 169 种旅行情境；P—W 是 8 份非旅行或混合任务，覆盖 98 种中的 94 种。也就是说，定义了的情境不一定都已经进入这 23 份任务。
  • Per diem：按天计算的餐饮补贴。 当前数据中，国外行程的餐饮按每日津贴处理，因此不能把同一段的餐饮收据再逐张重复报销。Trip E 的例子按 6 天处理。
  • 382 份材料、257 条费用、134 份不报材料、192 个 flags 是不同对象的统计，不应理解成文件与费用条目一一对应。

第 11 页 怎样判断 Agent 到底做对了没有

打开这一页

不是听 agent 说“我完成了”，而是把 Concur 里实际保存的结果读回来，与隐藏答案逐项比较。

  • 左边截图说明：酒店条目保存成 1,120.60，备注解释了扣除，四晚也已经逐晚列出。
  • 中间是评分输出。这次 Trip A 通过了 87 个检查中的 84 个，得到 96.6%。
  • coverage 21/23：应该有的 23 条费用，找到了 21 条。
  • expense_type 21/21、basic_fields 21/21：找到的条目里，类型和基本字段检查通过。这个分母是已匹配条目，不表示缺失的两条也通过了。
  • itemization 检查酒店拆分；attendees 检查参会人；skip_respected 检查该忽略的材料是否被忽略；exclusions 检查需要扣除的金额。
  • flags_required 5/6：要求的六项提醒只完成了五项。这里缺了经济舱选座费需要说明的问题。
  • 另外还有一条 71.77 的费用没有匹配到预期条目，会作为额外警告显示。因此 96.6% 不等于整份报销单毫无问题。
  • submittable: True 是工具对可提交状态的判断，也不等于全部政策检查都通过，更不表示 agent 已提交。

右边是在区分几个记录对象。

  • Run / turn： 本页里一轮指令的一次执行有一份轨迹。Trip A 四轮合计 212 步、7.22 美元、约 24 分钟；这是完整任务的合计，不是每轮都花这么多。
  • Export： 从 Concur 读回来的实际报销结果。
  • Score： 各维度通过了哪些检查。
  • Ledger： 把同一种 situation 在不同批次的测试记录汇总起来。例如酒店个人费用情境历史上通过 3/3。
  • 有些内容没有自动评分，例如 business purpose 的具体措辞、Oracle alias、里程计算器字段、批准材料是否附上，需要人结合轨迹检查。

这样后面做加速实验才有共同尺度： 改完以后用了多少时间、钱、步骤，以及报销结果有没有变差。

第 13 页 为什么重复的模型调用值得优先优化

打开这一页

第 12 页看步骤，这一页进一步看这些步骤消耗了多少时间。

  • 同样的 15 次 trip-runs，记录的执行时间合计约 191.2 分钟，平均每份约 12.7 分钟；不计不同轮次之间用户停顿的空档。
  • 模型调用约 135.3 分钟，占 70.8%；浏览器工具约 52.0 分钟，占 27.2%；页面读取等约 3.8 分钟，占 2.0%。分钟数经过四舍五入。
  • 这说明：在这一批任务中，即使页面操作很简单，反复等模型返回也会累计很多时间。

中间五个框是在展示一个常见的普通费用条目。

  • 第一次调用点 Add Expense；第二次点 Manually Create；第三次选类型；第四次填表；第五次保存。
  • 126 条普通费用里，有 72 条出现了这套阶段顺序。普通费用这里排除了参会人处理、酒店拆分和里程等特殊工作。
  • 因此一个可以测试的改进是：把可预测的几步导航组织成一个操作，并在关键状态变化处检查是否成功。

底下两块要区分“发现”与“准备验证的办法”。

  • 发现是：一些常规阶段合计占 57% 的步骤、47.7% 的模型时间。
  • 准备验证的是：其中哪些调用能合并，合并后需要保留哪些检查。
  • 不能直接说能省掉 57% 的步骤，或者把 70.8% 的时间全部消掉。 这些统计只是定位候选环节，真正省多少还要跑对照实验，并检查分数有没有下降。

第 14 页 为什么还必须可靠地判断操作成功与否

打开这一页

合并操作之外，还有一种明显浪费：事情已经做成了，系统却告诉 agent 没做成。

左边是保存结果被误读。

  • Trip R 的第一条 395 美元费用已经保存，但 Concur 弹出 Not Found。
  • Agent 把它理解成没有保存，又开始重复保存；分析中这造成额外 124 步、约 4.20 美元。
  • 最后它甚至请用户手动添加，存在重复报销条目的风险。
  • 前面提到的“60 次重复保存”，数的是保存尝试；这里的“124 个额外步骤”，数的是模型调用及周边处理，不是互相矛盾的两个数字。
  • 这个异常轮次总共 135 步，已从前两页的常规运行平均值里排除。

右边是下拉框反馈被误读。

  • 工具说 No option matched，但 93 条这类反馈中，有 20 条在下一次观察里已经能看到选中的值。
  • 如果 agent 只相信报错文字，就可能再选一次，甚至把正确值改错；货币选择曾在 USD 与 GBP 之间来回切换。
  • 这是历史反馈消息的统计，不能把 20/93 当作前面那 15 次运行的操作失败率。

目前改了什么，以及还缺什么？

  • 保存逻辑已经增加“去列表里确认条目是否存在”和重试保护；效果仍需要真实运行对比。
  • 下拉框已修改为区分“确实没匹配上”和“选择尚未确认”，并读回实际值；仍需要对应测试与真实环境验证。
  • 因此这两条方向要一起做：减少固定导航的重复调用，同时可靠地确认操作结果，避免成功之后还在返工。
  • 最后还是用同样的指标检验：时间、费用、步骤，以及报销结果质量。

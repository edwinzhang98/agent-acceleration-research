## 3 Exact E ledger additions and patches

Append the following records in the next dossier version. Existing E226, E230 and E271 retain their version-qualified evidence; no original line is silently replaced.

- **E304 — GEPA.** Agrawal et al., arXiv:2507.19457v2, 14 Feb 2026, §3/Algorithm 1. Execution traces and feedback support reflective prompt revision and candidate evaluation. Qualitative evidence for automated prompt improvement, not a measured enterprise Web time/cost gain. Primary: https://arxiv.org/pdf/2507.19457v2 ; author implementation: https://github.com/gepa-ai/gepa . Verified 29 Sep 2026.
- **E305 — ADIAS.** Jiang et al., arXiv:2608.06410v1, 3 Aug 2026, §3.3/§4/App C.2–C.3. Persistent issue state guides repeated diagnosis, full-code modification and evaluation. A close precedent for the proposed automatic improvement loop. Its reported step-based efficiency must not be relabeled as elapsed-time or dollar efficiency. Primary: https://arxiv.org/pdf/2608.06410v1 . Verified 29 Sep 2026.
- **E306 — Darwin Gödel Machine.** Zhang et al., arXiv:2505.22954v2, 26 Sep 2025, §3/App C.3. Diagnoses coding evaluation logs, revises agent code, evaluates and archives candidates. Background precedent for code-level self-improvement; does not establish this project's Web acceleration result. Primary: https://arxiv.org/html/2505.22954v2 . Verified 29 Sep 2026.
- **E307 — ActionEngine v2.** Zhong et al., arXiv:2602.20502v2, 28 Sep 2026, §3–5. Constructs application state-machine memory, compiles executable plans and defines reactive repair with memory updates. Evaluated methods share a backbone; final evaluation follows task-template warm-up and disables the Patcher. Reports one-time crawling cost and amortization, not an explicitly established all-in continual-learning bill. Preserve E226 as the v1 record; see D311. Primary: https://arxiv.org/html/2602.20502v2 . Verified 29 Sep 2026.
- **E308 — SkillWeaver mechanism and validation boundary.** Zheng et al., arXiv:2504.07079v1, 9 Apr 2025, §2–3/App D.2.1. Website exploration, skill practice, API synthesis and automatic test/debug loops provide a precedent for learned actions. Exception suppression can cause incorrect skills to pass verification, motivating task-outcome checks in the proposed design. Primary: https://arxiv.org/html/2504.07079v1 . Verified 29 Sep 2026.

## 4 Still open

- Agree whether the first study prioritizes automatic improvement selection, environment knowledge, or a narrowly specified interaction of both. The draft's efficiency ranking and explicit conditions are suggestions, not accepted design requirements.
- Inspect real traces for state/action/result, timing, token, outcome and version information. Identify the environment reset and independent scoring capabilities before selecting a protocol.
- Check official code availability and practical reproducibility before committing to literature baselines. Method adaptations must be labeled; a conceptual reconstruction is not a verified reproduction.
- Use equal initial evidence and permissions, then compare cumulative learning-resource budgets while logging each method's additional information gathering. Iteration counts alone are not equal budgets.
- Separate frozen held-out generalization from sequential online learning. Report human interventions as well as task speed/cost to test the user's automation objective.
- Treat the four-group study as component-bundle screening. Isolate efficiency prioritization with an additional matched ablation if claiming its specific effect.
- Check final draft with the user before estimating tasks, repeats, learning rounds, candidate counts, token usage, environment usage and training resources. No financial budget is proposed in this turn.

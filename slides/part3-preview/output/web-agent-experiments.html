WEB AGENT LEARNING EXPERIMENTS

Research problem and objective

Study scope: fixed model weights, interactive Web tasks and persistent learning across task instances.

Research question

How can prior interactions reduce the time and cost of later Web tasks while maintaining task success?

Why this needs an experiment

  • Repeated tasks may repeat discovery, reasoning or error recovery that earlier experience could help avoid.
  • Learning also costs time and money. Acquiring, checking and reading knowledge may outweigh what it saves.

Unit of evaluation
A sequence of new task instances, with the learning investment charged to that sequence.

Operational objective

Seek lower elapsed time and total cost, subject to a pre-specified quality requirement relative to the baseline.

Predefine the acceptable change in task success.
Success
Fraction of test tasks passing an external outcome check; compare paired success rates and report uncertainty.
Time
Elapsed time per task, including retries and failed runs. Report mean and tail latency.
Cost
Learning and validation investment, plus execution costs over the same task sequence.

N counts later tasks attempted. Learning includes validation; execution includes reading learned context.

APPENDIX A1 / MEASUREMENT PROTOCOL

Success, elapsed time and cost need separate checks

Proposed protocol. Specify thresholds and budgets before the held-out test; no experimental results are shown.

QuantityOperational definitionReport / control
Task successExternal check of the final saved state: requested fields correct, no duplicate record or unrelated change.Paired success rates with uncertainty; predefine an acceptable drop. Count correct-to-incorrect changes.
Task latencyElapsed time from task release to termination. Include model calls, browser/tool waits, checks and permitted retries.Mean, median and tail latency over all test tasks. Failed runs and timeouts remain in the report.
Learning investmentExplore or collect development traces; propose, test and select an update. Count the actual resources spent.Report learning cost and elapsed time separately. Amortize the one-time cost across the stated reuse horizon.
Execution costModel input/output charges, tool charges and billed environment use for all test executions, including failures.Include retrieval and reading the update. State price assumptions; report tokens and calls as diagnostics, not dollars.
Total cost & reuseLearning investment plus execution cost for the same number of subsequent tasks in both arms.Plot cumulative cost against tasks attempted. Report any break-even point together with achieved success.

Two different comparisons

  • Fixed test set: same tasks and execution limits, to isolate the update's effect.
  • Fixed total budget: let the baseline spend unused learning budget on execution; predeclare retry rules.

Keep evaluation independent

  • Freeze before testing. Hidden checker results cannot trigger Agent retries.
  • Count later maintenance as learning cost. Keep research-only scoring overhead separate.

Validation before reuse

  • Test candidate updates on validation tasks; retain a version only if it meets the quality rule.
  • Record provenance, update size and loading costs. Preserve the original version for comparison.

What remains a research question

  • Which observations or traces justify a general rule?
  • When should an update be revised or rejected?
  • Do later savings exceed acquisition, checking and use costs?

AGENT ACCELERATION · PART 1 · 02

The loop, with every term on it

here: the loop and its two equations → to: why the reading term grows fastest

One task = one loop run N times. Each pass observes the screen or page, makes at least one model call, acts, and waits. A call has three segments: queueing at the provider; reading the prompt — all tokens processed together, cheap per token; writing the answer — one token at a time, about 12 ms each (81.7 tokens per second measured for Claude Opus 5.5, Artificial Analysis, 2026) and 5× the read price.

Observation, action, waiting and queueing enter only the time equation; read and write tokens enter both. That asymmetry is the whole structure behind “how slow and expensive are linked”.

Npasses — task length, action granularity, idling
cmodel calls per pass — the harness (the program around the model): one call, or plan + judge + reflect
readtokens read per call — history length, screenshot size
writetokens written per call — thinking mode, model size
pricemodel tier, fast mode, cache (a cached read costs 0.1×)
observe · act · waitenvironment time — browser, desktop sandbox, fixed sleeps

AGENT ACCELERATION · PART 1 · 03

Reading grows with the square of the steps; writing only linearly

from the loop → here: the shape of the reading term → to: the five sources of slowness

Writing per step is roughly constant, so N steps write about N × W tokens — linear.

Reading at step k re-sends the k−1 earlier screenshots and messages — one screenshot is 1,000–1,800 tokens (Anthropic, 2026a) — so the sum over a task is about N²/2 times the tokens added per step: 10 steps read 55 step-units of history, 20 steps read 210 (calc.). Doubling the steps roughly quadruples the reading and only doubles the writing.

This assumes the full history is re-sent with no cache. Trimming history flattens the curve; prompt caching cuts the read price to 0.1× but leaves the shape.

I · TOO MANY STEPS (N)
318 tool calls per task
Hour-scale tasks take hundreds of passes: 318 tool calls per task on OSWorld 2.0 with one action per step (Claude Opus 4.7, 108 tasks); in a median text-agent task two thirds of the steps are pure navigation.
(XLANG Lab, 2026; Wong et al., 2026)
II · TOO MANY CALLS PER STEP (c)
4–12 planning calls per judging call
Harnesses that plan, judge and reflect make several calls per pass; sampling candidates multiplies them again; a coding agent makes 6.6 model calls per user turn.
(Abhyankar, Qi & Zhang, 2026; Liu et al., 2026)
III · EACH CALL IS SLOW
Queue, read, write, think
Identical requests vary up to 69× in latency by time of day; reading gets slower every step (up to 3×); writing one token at a time takes 91–98.6% of model time once the cache is warm; thinking modes multiply the writing.
(Bian et al., 2025; Abhyankar, Qi & Zhang, 2026; Yuan et al., 2026)
IV · THE ENVIRONMENT IS SLOW
3–26 s per observation · 6.6 s per browser action
Building an accessibility tree, executing in the browser, sleeping a fixed 2–3 s after every action, and tool runs with a long tail: 4% of tool calls take 85% of tool time.
(Abhyankar, Qi & Zhang, 2026; Wong et al., 2026; Zhu et al., 2026)
V · EVERYTHING IS SERIAL
concurrency within a turn: 1.15
Observe, decide, act and wait run strictly one after another, so task time is the sum of the four classes above; fixing one term saves only its own share — which is why the shares (page 10) must be known before anything is accelerated.

AGENT ACCELERATION · PART 1 · 05

I · Too many steps

from the five classes → here: why the number of passes N gets large → to: calls per step

N multiplies everything. It gets large in five ways: the task is long; each pass does a single action; navigation-only passes still go through the model; the agent idles or loops; it acts on a stale screen and has to redo the work.

I-1, I-2 · LONG TASKS, ONE ACTION PER PASS
318 tool calls per task, mean
OSWorld 2.0, 108 long desktop tasks, Claude Opus 4.7 with maximum thinking, one action per step, 500-step cap. Letting one call issue several actions cuts the same model to 160.7 steps and Claude Opus 4.8 to 103 steps (481.8 calls).
(XLANG Lab, 2026)
I-3 · NAVIGATION-ONLY PASSES
66.7% of steps are pure navigation
Median task across 151 WebVoyager tasks on live websites, three text agents (Browser-Use, AgentOccam, WebVoyager) driven by GPT-4o: paging, scrolling and opening the next page each cost a full model call.
(Wong et al., 2026)
I-4 · IDLING AND DEAD LOOPS
66% of steps wasted; one loop = 27 min, $8.47
GTA1 harness (o3 plans and judges, GTA1-7B locates elements) on 39 OSWorld desktop tasks: in failed tasks that ran past 50 steps, 66% of steps were repeats; one element-locating loop repeated the same step 18 times — 27 minutes and $8.47 at list price without caching.
(Abhyankar, Qi & Zhang, 2026)
I-5 · ACTING ON A STALE SCREEN
a recorded failure mode, share not reported
A screenshot taken before the page has changed leads to a click on the old layout and a repair afterwards; OSWorld 2.0 records “stale interface state” as one of its failure modes but gives no share.

AGENT ACCELERATION · PART 1 · 06

II · Too many calls per step

from the number of passes → here: model calls per pass, c → to: what happens inside one call

c multiplies N. A harness that plans, judges and reflects makes several calls per pass; sampling several candidate actions per step multiplies the calls again; coding agents call the model many times inside one user turn.

II-1 · PLAN + JUDGE + REFLECT
4–12 planning calls per judging call
GTA1 runs four parallel planners per step, retries up to three rounds, then one judging call picks; Agent S2 adds a reflection call per step, so planning takes 53% and reflection 34% of task time. Both measured step by step on 39 OSWorld desktop tasks.
(Abhyankar, Qi & Zhang, 2026)
II-2 · SAMPLING CANDIDATES

(Lee et al., 2026)
II-3 · CODING AGENTS

AGENT ACCELERATION · PART 1 · 07

III · Each call is slow: queueing and reading

from calls per step → here: the first two segments of a call → to: writing, thinking, model size

Two segments before a single token is produced. Queueing at the provider costs nothing but counts as model time. Reading re-processes the entire history on every call, so it grows with the step number, with the size of each observation, and with whatever the cache failed to keep.

III-1 · QUEUEING
up to 69× latency spread for the same request
Client-side measurement of 15 models across 5 providers: requests of equal length, sent at different times of day, differ in latency by up to 69×. Not billed; usually reported as “model time”.
(Bian et al., 2025)
III-2 · READING GROWS WITH THE STEP
later steps up to 3× slower · 4.8× input when the observation is rich
OSWorld-Human: in the multi-call harnesses the prompt at step k carries the k−1 earlier screenshots, and the authors attribute the slowdown to the reading segment (“dominated by prefill”). AgentSysBench: switching one WebArena agent (Kimi-K2.6) from a single observation format to accessibility tree (the text list of on-screen elements) + HTML + screenshot multiplied the input 4.8× and raised the model’s share of time from 46.9% to 61.6%.
(Abhyankar, Qi & Zhang, 2026; Chang et al., 2026)
III-2 · WHEN THE CACHE IS EVICTED
request latency up to 7.14× under load
SWE-Agent and OpenHands running GLM-4.6 on 8 H100s for SWE-bench Lite: as concurrency rises the cache of already-read prompt (the KV cache) is evicted and re-read, and request latency rises up to 7.14×.
(Kang et al., 2026)

AGENT ACCELERATION · PART 1 · 08

III · Each call is slow: writing, thinking, model size

from queueing and reading → here: the writing segment → to: the environment

Writing is one token at a time, so it is the slowest segment per token and the most expensive. Thinking modes add tokens that are written before the answer; larger models take longer per token. Neither reliably buys accuracy.

III-3 · WRITING DOMINATES A WARM CALL
91–98.6% of model time
One-call-per-step ReAct agents on five benchmarks, Qwen3.6-27B and Gemma4-31B served locally (vLLM serving engine, 2 H100s): with the cache warm, token-by-token generation takes 91–98.6% of the model’s time. Desktop agent UFO2 (GPT-4o / o1 API): about 10 s per model call, the largest item in every configuration.
(Yuan et al., 2026; Zhang et al., 2025)
III-4 · THINKING MODES
224K vs 37K output tokens per task
Same 108 OSWorld 2.0 tasks: Claude Opus 4.8 writes 224,000 output tokens per task, GPT-5.5 writes 37,000; the writing is billed as output and, on Claude Opus 5.5, cannot be switched off.
(XLANG Lab, 2026; Anthropic, 2026b)

accuracy fell in 21 of 36 comparisons

AGENT ACCELERATION · PART 1 · 09

IV · The environment is slow; V · nothing overlaps

from the model call → here: the three environment terms and the serial structure → to: which term dominates

Four environment terms and one structural multiplier. Observation: building the accessibility tree (the operating system’s text list of on-screen elements). Execution: the browser and the page load. Fixed sleeps: the agent cannot tell when a page is ready. Tool tails: tests and builds. And all of it runs strictly in sequence.

IV-1 · OBSERVATION
3–26 s per accessibility tree
OSWorld desktop applications; the screenshot itself is under 2% of task time. In UFO2, OmniParser element detection adds about 1 s per step.
(Abhyankar, Qi & Zhang, 2026; Zhang et al., 2025)
IV-2, IV-3 · BROWSER AND FIXED SLEEPS
6.6 s browser vs 4.7 s model per step · 2–3 s sleep after every action
Medians over 151 WebVoyager live-site tasks with GPT-4o. OSWorld’s environment code sleeps 2 s after each action and OSWorld 2.0 prescribes 3 s: 318 steps ≈ 16 minutes of pure waiting (calc.); a single-call GUI agent (Kimi-K2.6) spends over 70% of its OSWorld time inside the desktop sandbox.
(Wong et al., 2026; xlang-ai, 2026; XLANG Lab, 2026; Chang et al., 2026)
IV-4 · TOOL TAILS
4% of tool calls take 85% of tool time
4,265 Claude Code and Codex sessions from 43 developers, September 2025 – June 2026: a request averages 4.3 minutes, of which tools take 2.5 (59.8%) and the model 1.7 (41.0%).
(Zhu et al., 2026)
V · SERIAL
concurrency within a turn: 1.15
Copilot telemetry. Because the four stages never overlap, task time is the sum of every term above, not the largest one; fixing one term saves only its own share. Caution when reading “total time”: 80–92% of a coding session’s elapsed time is the human thinking between turns.
(Liu et al., 2026; Zhu et al., 2026)

How slow and expensive are linked: three kinds of relationship

from the two bills → here: what each cause does to time and to money → to: what fixing each lever buys

The two equations share the read and write tokens; environment time and queueing appear only in the time equation. So every cause relates to time and money in exactly one of three ways.

SAME SOURCE — in both equations
fix it, and time and money fall together
Steps N: time roughly linear, read tokens quadratic — double the steps, double the time, about 4× the read bill (uncached). Calls per step. Reading: history, screenshots, rich observations. Writing: thinking — the slowest and the dearest token. Cache hits: save both, but fragile — any edit to the history or a switch to fast mode invalidates them. Failures and idle loops: both, and they turn “per attempt” into “per success”.
(Abhyankar, Qi & Zhang, 2026; Anthropic, 2026b)
SLOW BUT NOT EXPENSIVE — time equation only
fix it, and only time falls
Queueing. Page loads and fixed sleeps. Tool tails (tests, builds). None of these produces a token. The machine time behind them is billed by the hour: CPU sandboxes $0.02–0.36 per hour, usually under 5% of the API bill (page 15). To escape the queue one buys a fast or priority tier — at 2× the price.
MONEY FOR TIME OR FOR ACCURACY — opposite signs
buying speed buys only the writing segment
Fast mode: up to 2.5× faster writing (vendor-stated), reading and queueing unchanged, 2× the price. Bigger models, more thinking: slower and dearer, and the cost-versus-accuracy curve is convex — each extra point costs more than the last: on one model the marginal tokens per point rise from 101K to 575K; 6×, 9× and 9.6× the tokens for a few points; and more thinking is not always more accurate. Smaller models: faster and cheaper, but if accuracy falls, steps and retries rise — possibly slower and dearer again (inference; no direct evidence).
(Anthropic, 2026b; OpenAI, 2026; XLANG Lab, 2026; Kapoor et al., 2025; Lee et al., 2026)

moneyN steps c calls × ( read tokens × price + write tokens × 5 × price ) ÷ success rate

In one line: a cause that lives in tokens — fix it and time and money fall together; a cause that lives in waiting — fix it and only time falls; paying for speed buys only the writing segment.
